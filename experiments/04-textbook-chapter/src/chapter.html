4.1 Before you begin: what is a turn?

prerequisite · not changed by #127

A daemon worker thread keeps one TypeScriptBackend alive across commands. Each command refreshes it, then asks questions. The six caches hold answers for exactly that stretch.

turn
One successful backend.refresh plus every query until the next one. In the daemon: one command execution.
transient resources
Memory that can be rebuilt on demand: the six caches, and TypeScript programs held by the project graph.
release
releaseTransientResources(): drop transient resources between commands.
handle
One cache created by the scope. getOrCreate(key, create) is its entire API.

Why answers must die with the turn real run · #127 build

Turn 1 asks for references to target. Then app.ts gains a third line calling target, the backend refreshes, and the same question is asked again.

Normal build: caches emptied at turn 2

Same build, emptying disabled in memory

Not new in #127: main and #126 empty the caches at the same point (Worked example steps 7–8 match on all three builds). This PR changes who empties them.

Receipts:
  • worker handles one message at a time: apps/cli/src/daemon/daemon-navigation-worker-entry.ts:60 this.tail = this.tail.then(() => this.handle(value))
  • command refresh: apps/cli/src/workspace-request-scope.ts:52 → packages/core/src/backend/backend-router.ts:33 → typescript-backend.ts:79–83
  • release at a turn boundary: apps/cli/src/daemon/daemon-resource-monitor.ts:248–258, workspace-request-queue.ts:87; worker side daemon-navigation-worker-entry.ts:150–165
  • stale run: probe/semantics.mjs … clearing-disabled replaces cacheScope.beginTurn with a no-op; output probe/out/semantics-head-clearing-disabled.json

4.2 A metaphor that mostly holds ≈ lossy

intuition
ClassroomCode
Question already on the board: point at itgetOrCreate finds the key; no search runs
Writing "pending…", filling in laterA Promise is stored at once; it settles later, in place
Answer "can't be done" stays writtenA rejected Promise stays for the rest of the turn
Teacher interrupted before writing: board stays blankFactory throws synchronously: nothing stored, next ask retries
Bell rings but the lesson plan didn't load: boards keptRefresh fails: no beginTurn, previous turn's answers remain

Where it breaks: one question can read two boards (callers read the references board); boards are keyed by exact strings, not meaning; a real lesson has no "pending" answer that settles after the bell and gets ignored.

4.5 Six handles, one key

mechanism

Real keys and stored values after one turn of queries on the #127 build real dump.

HandleReal keyStoresFilled byAlso read by

Why six handles, not one map (decision 3)

Five rows share the string src/lib.ts::target, each with a different value type. One shared map would need a query prefix in every key. PR's reason: "independent key and value spaces".

Why Map.has changes nothing here (decision 7)

Every stored value is a Promise or an array, so never falsy. #126's if (existing) and if (!locations) behaved exactly like has. The difference appears only for a future cache storing undefined, as the core test does.

Receipts: probe/cache-keys.mjs → probe/out/cache-keys-head.json; key format packages/core/src/intermediate-representation/canonical-identity.ts:29–34; callers read references via typescript-semantic-query-service.ts:110–114; positions read by findCallees through definitionNodesOf :134–160.

Context for decisions 1 and 5

4.9 Decisions in depth

judge · same 12 as 4.0

Each card: what was chosen, the reason if one exists (verbatim), what is new versus kept, and the facts that bear on it. No card says whether a choice is right.

1 · Backend release waits for project release and carries its failure unexplained behavior

Chosenawait this.semanticQueries.releaseTransientResources() (backend:88) and await this.projects?.releaseTransientResources() (service:131).
Reason
None found. The PR body shows it (After diagram: "awaited release boundary"; public surface: releaseTransientResources(): Promise<void>) and commit 5 is titled "Specify awaited semantic resource release", with no body.
vs buildsReal: main rejects · #126 resolves, unhandled rejection, worker dies · #127 rejects. With async project release: main and #126 resolve before it settles; #127 waits. Table 4.1
Asked for?Spec asks core to own the turn-scoped cache lifecycle and keeps every failure path unchanged; behavior fixes go to the follow-ups spec, which has no entry for this.
WeighFor today's synchronous TS projects this restores main. For async projects it is a new contract. Both readings are supported by the runs.

2 · Failure asymmetry becomes core's generic contract stated as preservation

ChosengetOrCreate stores whatever the factory returns, including a Promise that later rejects or an empty result; a synchronous throw stores nothing; clearing never waits for or listens to old Promises.
Reason
"this layer moves only cache lifetime out of TypeScript while preserving all six algorithms, key spaces, promise/value identities, and failure behavior."
Kept?Yes. Steps 5–6 match on all builds; the 5 characterization tests pass on #126 code (10/10).
WeighEvery future TurnScopedCacheScope consumer inherits sticky rejections for a whole turn. The PR does not discuss other consumers; at #149 there are none.

3 · One scope with six handles, not one shared map stated

ChosencreateCache<Key, Value>() called six times on one scope (service:32–55).
Reason
"Chose one scope with six handles over one shared map, because the existing queries have independent key and value spaces."
FactsFive handles hold the identical key src/lib.ts::target with five value types (4.5, real dump). The PR names the shared map as the alternative; no other alternative is discussed.

4 · Scope exported from @symnav/core stated by spec

Chosenexport { TurnScopedCacheScope, type TurnScopedCache } (core index.ts:152).
Reason
Spec: "Shared in core: … turn-scoped query cache lifecycle." (plans/005/daemon-architecture-functional-spec.md:58–60)
FactsNo new package dependency: the service already imported @symnav/core. Consumers: 1 (TS semantic query service) at #127; still 1 at #149, where scope and service files are byte-identical to #127.

5 · Empty caches synchronously, before awaiting project release stated

Chosenservice:130 this.cacheScope.releaseTransientResources() then :131 await this.projects?.releaseTransientResources().
Reason
"Chose synchronous cache clearing before project release over clearing after the await, because released semantics must be unavailable while release is pending or rejecting."
Kept?Order kept: #126 and main also cleared first (base service:126–127). The await is decision 1.
WeighThe pending window exists only with async project release. TS projects release synchronously; the daemon worker, the only production caller, runs release and commands one at a time. The PR's test opens the window with a fake async graph. The core interface and the spec's future hosts allow async.

6 · Next turn begins only after refresh succeeds stated

ChosenbeginTurn stays the last statement before return in refresh (backend:83).
Reason
"Chose to begin the next turn only after refresh succeeds over clearing at refresh entry, because failed refresh must preserve the current successful turn."
Kept?Same position on main and #126. New test "preserves the current turn when backend refresh fails" passes on #126 code. Real: steps 10–11.

7 · Map.has before Map.get, not truthiness stated

Chosenif (this.values.has(key)) return this.values.get(key) as Value; (scope:15).
Reason
"Chose Map.has before Map.get over truthiness checks, because undefined is a valid cached value."
FactsAll six TS handles store Promises or arrays; none can be falsy, so the old truthiness checks behaved identically. Core test "returns each exact factory value once per key and handle" caches undefined.

8 · beginTurn(files) replaces beginTurn(snapshot) unexplained

ChosenbeginTurn(files: readonly WorkspaceFile[]) on the exported TypeScriptSemanticQueryService (service:63).
Reason
None found; listed under "Public surface" without a reason.
FactsOld body used only snapshot.files (base service:50). Only caller: TypeScriptBackend.refresh. The final commit edits four test call sites to match.

9 · Scope created inside the service, not injected unexplained

Chosenprivate readonly cacheScope = new TurnScopedCacheScope(); (service:31).
Reason
None found. PR diagram: "Service owns Scope".
FactsBackend, router and daemon reach the caches only through the service's beginTurn and releaseTransientResources. Other shape (this chapter's example, not discussed in the PR): the backend creates the scope and passes it in.

10 · Handles expose only getOrCreate unexplained

ChosenExported interface TurnScopedCache has one method (scope:1–3). clear() lives on the internal TurnScopedCacheHandle.
Reason
None found.
FactsNo way to invalidate one handle or one key. Invalidation is all six at once.

11 · Scope's beginTurn() and releaseTransientResources() share one body unexplained

ChosenBoth call this.clear() (scope:35–41).
Reason
None found.
FactsCore test "clears every handle at turn and release boundaries" pins both names, including a double release.

12 · File lives in core/src/backend/ unexplained

Chosenpackages/core/src/backend/turn-scoped-cache-scope.ts.
Reason
None found.
FactsNeighbors: backend-router.ts, language-backend.ts, revisioned-backend-state.ts, errors.ts.
