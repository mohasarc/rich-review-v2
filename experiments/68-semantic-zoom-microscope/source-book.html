92class ResponsiveRoutingGuard implements DaemonRoutingGuard {
93  async evaluate(context: DaemonRoutingContext): Promise<DaemonRouteSnapshot> {
94    const record = context.readRecord()!;
95    let observation: DaemonObservation;
96    try {
97      observation = await context.observe(record);
98    } catch {
99      return { kind: "cold", reason: "recovering" };
100    }
101    if (observation.kind === "responsive") {
102      if (observation.pong.symnavVersion !== context.productVersion) {
103        return { kind: "fallback", reason: "incompatible" };
104      }
105      if (observation.pong.state === "starting") {
106        return { kind: "cold", reason: "recovering" };
107      }
108      return { kind: "warm", record };
109    }
110    if (observation.kind === "starting") return { kind: "cold", reason: "starting" };
111    if (observation.kind === "unresponsive") return { kind: "cold", reason: "recovering" };
112    if (observation.kind === "exited") {
113      try {
114        context.removeIfProcess(record);
115      } catch {}
116      return { kind: "fallback", reason: "dead" };
117    }
118    return { kind: "fallback", reason: "incompatible" };
119  }

1# Symnav Daemon Architecture Functional Spec
2
3## Goal
4
5Restructure the merged daemon work so each concern lives in the package that owns it: a self-contained daemon package that knows nothing about symbols, a core that knows nothing about daemons, a TypeScript backend that holds only TypeScript-specific logic, and a CLI app that only composes. The daemon's user-facing behavior is defined in `daemon-functional-spec.md` and does not change. This is refactor work: not a rewrite of the daemon, not a change to any command's output or timing, and not a new language backend. This spec defines product behavior for contributors and hosts of the packages; implementation choices live in the phased plans.
6
7## Primary User
8
9**Contributors** changing symnav. Their default experience: a package boundary tells them where a concern belongs, and the build refuses an import that crosses the locked dependency graph.
10
11**Hosts** composing the packages into a runnable product. The CLI app is the first host. A future host (editor extension, MCP server, benchmark harness) composes the same packages the same way. No host reaches into another package's internals.
12
13End users of the `symnav` binary observe no change from this work.
14
15## Core Guarantees
16
17### Behavior is unchanged
18
19This is a refactor. Every command, daemon lifecycle action, diagnostic record, telemetry event, and failure path behaves as it does today.
20
21```text
22Given the same workspace, arguments, environment, and daemon state, output bytes,
23exit code, execution mode, and lifecycle outcome are identical before and after.
24```
25
26Correct: a restructuring change passes the existing e2e parity and daemon suites without touching a single expectation. Incorrect: a restructuring change "fixes" a queue, eviction, timeout, or path while moving code.
27
28There is no "it was obviously a bug" override. Behavior defects found during restructuring are recorded in `daemon-follow-ups-functional-spec.md` and changed separately.
29
30### The daemon package depends on nothing internal
31
32The daemon package imports no other symnav package. It moves bytes for an executor it is handed; it does not know what a symbol, workspace snapshot, or backend is.
33
34```text
35@symnav/daemon may import: (nothing internal)
36```
37
38Correct: the daemon logs a worker's refresh counters as an opaque diagnostics record supplied by the executor. Incorrect: the daemon's protocol names a core type to describe those counters.
39
40There is no exception for "just a type".

42### Core knows nothing about daemons or processes
43
44Core answers questions about a workspace and its symbols. It has no concept of a background process, socket, registry, warm-up, or route. Retaining state across requests means keeping a core object alive; core does not ask its host how to persist anything.
45
46```text
47Core has no persistence port, no daemon port, and no notion of warm vs cold.
48Warm = the same session object answers again. Cold = a new session object.
49```
50
51There is no persistence abstraction until a second consumer of one exists.
52
53### A language backend holds only language-specific logic
54
55A concept that another language could share lives in core as a base the backend extends. The backend supplies only what depends on the language's toolchain.
56
57```text
58Shared in core: file revision tracking, prepared-file index, declarations-by-identity,
59transactional index publication, project-membership graph with input invalidation,
60turn-scoped query cache lifecycle.
61TypeScript-only: extraction from TypeScript syntax trees, tsconfig parsing (extends,
62references, path aliases, include/exclude), program and language-service creation,
63semantic query bodies.
64```
65
66### The CLI app is composition only
67
68`apps/cli` parses command-line syntax, resolves environment (state directory, daemon enabled), creates concrete dependencies, wires packages together, and prints. It holds no daemon policy, no workspace policy, and no navigation logic.
69
70```text
71A decision about routing, admission, ownership, delivery, memory, or lifetime that
72lives in apps/cli is a defect.
73```

76
77Numeric limits (memory caps, spool caps, deadlines, idle timeout, probe timeout, trace retention, replacement circuit, reattachment attempts) live in one policy object inside the daemon package, each with a stated reason in a policy record under `plans/`. 78
79```text
80No CLI flag, environment variable, or config file tunes a daemon threshold.
81```

113## Interaction Model
114
115### What a host provides to the daemon package
116
117- An executor: given argv, working directory, and telemetry flag, produces an ordered stream of stdout/stderr byte records and an exit code; can also release transient caches on request.
118- The location of a module that constructs that executor, so the daemon's worker can load it in another thread or process.
119- A state directory path.
120- The product version, for compatibility checks.
121- Per invocation: a workspace root and argv, or a control action (`start`, `status`, `stop`).
122
123### What a host receives
124
125- `execute(workspaceRoot, argv)`: a result identical in bytes to local execution, produced warm, cold, or by fallback. The host does not learn which route was taken except through the execution mode recorded for telemetry.
126- `control(action)`: a lifecycle report the host renders.
127
128### What a host must not do
129
130- Read or write registry, socket, spool, or log files directly.
131- Decide warm vs cold.
132- Import from the daemon package's internal modules; only its public surface.

2
3## Goal
4
5Symnav keeps a reusable workspace daemon so repeated navigation commands avoid rebuilding the same project state. Ordinary commands never wait for daemon startup: they answer locally while one daemon warms in the background, then later commands switch to the ready daemon. This must remain useful on representative workspaces and on projects up to ten times larger. The daemon is not a language server, a network service, or a new navigation surface. This spec defines product behavior only and avoids implementation choices.
6
7## Primary User
8
9The first-class user is a coding agent issuing many symnav commands during a long development session.
10
11Its default experience is:
12
13- First command starts one background warm-up and answers locally.
14- Further commands answer locally while warm-up continues.
15- Commands use the daemon after it becomes ready.
16- No navigation output reveals which route answered it.
17
18Explicit alternatives are `symnav daemon start|status|stop` for lifecycle control and `SYMNAV_DAEMON=0` for fully local execution.

20## Core Guarantees
21
22### Ordinary commands never wait for warm-up
23
24An ordinary command starts local execution without waiting for a daemon to become ready.
25
26```text
27If no ready daemon exists when a command is accepted, that command answers locally while one daemon warms independently.
28```
29
30The route chosen when a command is accepted does not change midway through that command. A daemon becoming ready does not cancel or duplicate local work already in progress.
31
32Examples:
33
34- First `resolve` in a large workspace starts warm-up and runs locally at once.
35- A second `overview` issued ten minutes into a twenty-minute warm-up also runs locally at once.
36- First command after readiness uses the daemon.
37- A warm-up failure does not delay or alter local command output.
38
39There is no flag that makes ordinary navigation commands wait for warm-up.
40
41### One durable warm-up per workspace
42
43Concurrent callers share one warm-up. Initiating caller does not own daemon lifetime.
44
45```text
46For one workspace and state location, at most one daemon is starting or ready, regardless of caller count or caller lifetime.
47```
48
49The daemon continues warming after initiating command exits. Later callers observe or adopt that warm-up; they do not restart it. A caller failure, timeout, or disconnect cannot stop a healthy warm-up.
50
51Examples:
52
53- Ten commands begin together in a cold workspace. All ten answer locally and exactly one daemon warms.
54- Initiating process exits one second after launch. Warm-up continues to readiness.
55- A healthy warm-up takes twenty minutes. It is not discarded because of project size or elapsed time.
56- Warm-up process exits. Starting state is cleared promptly and a later eligible command may try again.
57
58There is no healthy-startup timeout override because healthy automatic warm-up has no project-size deadline.
59
60### Warm answers equal local answers
61
62A command answered by the daemon produces the same stdout, stderr, and exit code as the same command run locally against the same workspace state.
63
64```text
65For any command, arguments, cwd, and workspace contents:
66output(daemon) == output(local), byte for byte, including exit code.
67```
68
69Warnings, errors, `--help`, `--version`, and `--json` are covered. There is no daemon-only navigation output and no local-only navigation output.
70
71There is no parity override.
72
73### Answers reflect current workspace state
74
75Every request sees workspace contents current when its execution turn begins.
76
77```text
78A request never answers from workspace state older than start of its execution turn.
79```
80
81For local commands, execution turn begins when local execution starts. For queued daemon commands, it begins when command reaches front of queue.
82
83Examples:
84
85- A file edited after one request is reflected in next request.
86- A queued request sees edits completed before its queue turn begins.
87- Added, deleted, and renamed files appear in next answer.
88
89There is no stale-data override.
90
91### Nested Git workspaces are separate boundaries
92
93Selected workspace is nearest Git workspace containing caller. A descendant directory with its own Git workspace marker belongs to a separate workspace.
94
95```text
96Parent commands never traverse, index, refresh, or return files from a nested repository, worktree, or submodule.
97```
98
99This boundary is independent of ignore rules. Ignore negation cannot pull a nested workspace back into its parent.
100
101Examples:
102
103- A parent repository containing `.worktrees/feature` does not return symbols from that worktree.
104- Running with `--cwd .worktrees/feature` selects and navigates worktree normally.
105- Directly targeting a nested-workspace file from its parent fails with guidance to select nested workspace.
106- A directory named `.worktrees` with no nested Git workspace remains ordinary workspace content.
107
108There is no include-nested-workspaces override.
109
110### Slow or busy does not mean dead
111
112Long startup, queue wait, and command execution are not daemon failures.
113
114```text
115Only authenticated evidence of process exit, protocol incompatibility, or corrupt communication invalidates daemon ownership.
116```
117
118A caller timeout or disconnect does not remove a live daemon record, stop a healthy daemon, or replay accepted work locally. A short command queued behind long work cannot destroy daemon state.
119
120Lifecycle status remains responsive while navigation work is running and reports daemon as busy rather than absent.
121
122There is no force-invalidate-on-timeout override.
123
124### Resource failures are controlled
125
126Supported workloads do not end with raw out-of-memory output, partial responses, or an unreported daemon disappearance.
127
128```text
129A resource or response-size limit produces either a complete normal answer or a complete symnav error while preserving recoverable daemon state.
130```
131
132Known capacity failures are not immediately repeated through equivalent local execution. A large response does not by itself mark daemon corrupt.
133
134There is no raw-failure override.
