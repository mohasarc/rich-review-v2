Keep the rest of the change in view.

Reasons are stated only where the supplied prose gives one.
01

Lifetime moves. Query ownership stays.

Core now supplies the lifetime class. Each TypeScript query service owns one scope and six isolated handles: definitions, reference locations, call targets, callers, callees, and position definitions. Algorithms and key spaces stay in TypeScript; its existing dependency on core remains.

Stated: core owns generic lifetime; independent key/value spaces need separate handles. Unexplained: composition via a scope instead of the spec’s proposed extension shape.

One service, one scope, six handles ↗Base service owns Maps ↗Supplied PR body and commit subjects ↗Core ownership statement ↗Extension shape proposed in the spec ↗
02

A lookup keeps the exact factory value.

Same key + same handle + same turn returns the stored value. Five stores use symbol-identity keys; position definitions use path + offset. Empty results and undefined count as entries. Rejected promises remain cached; a synchronous factory throw stores nothing, so the next call retries.

Stated: preserve existing key, identity and failure behavior; Map.has admits cached undefined. No new retry or cancellation policy is added.

The exact lookup and clear operations ↗One service, one scope, six handles ↗Position rehydration and reference-location lookup ↗Identity, failure, clear and old-settlement tests ↗Supplied PR body and commit subjects ↗
03

Clearing forgets entries. It leaves held promises alone.

beginTurn and scope release synchronously clear all handles, which remain reusable. A caller’s old promise can still settle; its settlement cannot overwrite a newer entry. This identity pattern is preserved in the base/head service recording. The ritual isolates one handle; it does not model garbage collection or cancel work.

Stated: preserve promise/value identities and failure behavior. The new core test pins old settlement versus a new entry; no separate reason for that exact test case was supplied.

04

Stored identity is not every public return’s identity.

References project cached locations on each call. Position definitions rehydrate nodes into a new array, including empty results. The four other identity queries return their stored promises directly. Backend async wrappers are a different observation surface.

Stated: preserve existing algorithms and identities. Unexplained: the historical reason for these different projection shapes.

Reference projections ↗Position rehydration and reference-location lookup ↗One service, one scope, six handles ↗Direct stored-promise returns ↗Backend async wrapper surface ↗Six added service tests ↗
05

Only a successful refresh begins the next turn.

Backend refresh clears after the awaited refresh work succeeds. A failed refresh keeps the successful turn’s entries. The exported service now takes readonly files rather than the whole snapshot.

Stated: failed refresh must preserve the current successful turn. Unexplained: why narrow the public beginTurn argument in this layer. The clearing order is preserved, not newly invented.

Backend success and release boundaries ↗Base backend boundaries ↗One service, one scope, six handles ↗Six added service tests ↗Supplied PR body and commit subjects ↗
06

Cache clear and project cleanup have separate endings.

Both versions clear before project cleanup. Head adds await through backend → service → project graph: pending cleanup keeps backend release pending, and cleanup rejection reaches that caller. Base returns early. The graph accepts async cleanup; the concrete TypeScript project cleanup here is synchronous.

Stated: clear first so released semantics are unavailable during pending or rejecting cleanup. Unexplained: reconciliation of the new completion/rejection behavior with the spec’s behavior-preservation rule. The ritual’s finger release means injected work settlement, not this cleanup call.

Clear before project release ↗Base project release is unawaited ↗Backend success and release boundaries ↗Base backend boundaries ↗Graph awaits asynchronous project cleanup ↗Concrete project cleanup is synchronous ↗Behavior preservation rule ↗Supplied PR body and commit subjects ↗
07

Callers get lookup; the scope gets clear.

Core exports TurnScopedCache with getOrCreate and TurnScopedCacheScope with createCache, beginTurn and releaseTransientResources. The scope retains registered handles and clears their Maps synchronously. Service release changes from void to Promise<void>.

Unexplained: the exact public API and registration structure. The stated core-ownership goal explains the move, not each API choice.

The exact lookup and clear operations ↗Core export ↗Clear before project release ↗Base project release is unawaited ↗Supplied PR body and commit subjects ↗
08

The tests add contracts; they do not demonstrate full parity.

Six files change (+391/−67). Four core cases and six service cases are added. The five original service tests and their helpers are byte-identical; no tests are deleted or weakened. The focused head run passes 15 tests. Controlled recordings use injected work/state, not a daemon or full workspace run.

Stated: commits characterize identities and specify lifecycle/awaited release. Unexplained: why this exact test selection is sufficient; no end-to-end parity claim is made here.
