**A. A prediction needs conditions and outcomes, not a topic label.**

[49](../49-follow-next-49/index.html) is the clearest advance since [47](../47-critique-refresh-40/critique.md). The original 23 outline names authentication exceptions without saying which requests belong to them. Its revised sentence names the token partition. The original 29 overview names clock ownership; the revision distinguishes the standalone queue's changed default from an already-monotonic process injection. Two fresh agent sessions received each version. The revised readers could make the targeted predictions before descent; the original readers needed the deeper prose. The [protocol](../49-follow-next-49/protocol.md) preserves the prompts, fixed conditions, source withholding, and seals.

That observation does not make the two entire pages complete. All four readers still needed 23/D04 to learn that host policy is optional. Source first supplied its default. I independently opened the original D04: the Public client room and D04 leaf name “optional policy”; `options.policy ?? DaemonPolicy.currentSystem()` appears in the embedded runtime evidence. The root's “executor/environment inputs” does not carry that authority/default decision. [50, row 04](../50-recombine-angles-50/index.html#comparison) now names both.

A concrete replacement for that part of 23's parent could say:

> The host supplies execution and environment. It may also supply policy; otherwise the client creates policy from the current system. Portable declarations hide a Node runtime whose loading begins at construction.

This is an editorial proposal, not an author rationale or a complete repair of the room. The [pinned runtime](reading/sources/client-runtime.ts), lines 85–100, supports the policy consequence. Its separate reason remains unexplained unless a source supplies one. Layout would need inspection: 49's longer credential statement already leaves little spare room in the fixed canvas.

Keep false learning separate from missing learning. [01's stack heading](reading/01-unconstrained-a--index.txt) says the first configured owner wins; [22](reading/22-game-any--game.txt) repeats “first configured ownership.” The [actual primary-owner loop](reading/sources/primary-owner.ts), lines 319–340, appends every owner but overwrites primary on each visit: the last configured owner wins. 49 shows that readers can apply the wrong first-owner statement quite consistently. Successful teach-back therefore needs an independent source check.

Likewise, [04](reading/04-textbook-chapter--index.txt) says “PR body silent” at 4.0 and “The PR body shows it” at decision 1 in 4.9. The [supplied body](reading/sources/pr-127-body.md) explicitly shows the awaited boundary. This is an actual parent/child attribution conflict. A long top is a different issue: rule 4 sets no viewport or word limit.

The remaining cost is visible: nine complete fronts are still a substantial reading task. Their authored mappings do not prove that every qualification in an original bullet is announced above it. **D. Keep different relationships; remove repeated explanation.**

The repeated shell is orientation → complete register → mechanism → source. It is not inherently bad. The useful variety is what a reader can see or do inside it.

There is also a new concrete representation problem in 52. In both static maps, the arrow goes from `packages/daemon` down to CLI composition and reads **“imports / constructs.”** The caption calls these selected dependency edges. CLI composition imports/constructs the policy; the package does not import/construct the CLI. The diagram can keep that direction and name policy supply, or show the dependency in the reverse direction. [The screenshot](reading/52-critique-response-52--compact.png), [generator at line 65](../52-critique-response-52/build.py), and [pinned CLI source](reading/sources/program-policy.ts), lines 7 and 77, preserve the witnesses. <a id="e"></a>
**E. A human needs a choice to reconsider, not just a mechanism to recite.**

The corpus is strongest at “what happens?” and recovering “what reason was recorded?” It is weaker at showing how the answer interacts with context the author lacked. 49's prompted predictions are useful, but they do not ask a reader to select the consequential design question. 51's nine examples likewise mostly reproduce the selected mechanism.

11, 16, 29, and 35 offer ingredients for that missing step. A narrowly labelled hypothetical could ask a new host to require reproducible policy across machines, then follow the relation between optional facade policy, current-system fallback, required internal slices, and process serialization. The reader could explain which seam needs a decision and which existing mechanism already supports it. A transcript or PR passage would still be required to call any rationale the author's.

This should remain a read-only teaching activity. Philosophy's eventual reader response is deliberately postponed by rule 2. Missing approve/reject buttons or comment storage is compliance with this brief, not a failure to implement the philosophy.
