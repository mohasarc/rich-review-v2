01
STATED
Move lifetime into core.
↗

The TypeScript service still owns query algorithms and its own cache instance. Core now supplies the shared emptying mechanism. No package dependency direction changes.

Reason: The architecture spec assigns language-independent cache lifetime to core; semantic query bodies stay in TypeScript.

02
STATED
Keep six stores separate.
↗

Five stores use formatted symbol identities; the sixth uses file + source position. Definitions, reference locations, call targets, callers, callees, and position definitions keep their existing algorithms and value spaces.

Reason: The PR explicitly chooses separate handles because existing queries have independent keys and values.

03
STATED
Cache the exact returned value.
↗

Presence, not truthiness, decides a hit: undefined and empty arrays count. Repeated lookups return the stored object or promise without wrapping it.

Reason: The PR says undefined is a valid cached value and calls for preserving promise/value identities.

04
STATED
Retain the two failure shapes.
↗

A returned promise stays cached after rejection. A factory that throws before returning creates no entry, so the next lookup retries. This preserves query behavior; it does not describe the changed release promise.

Reason: The PR calls for preserving query failure behavior; new characterization tests pin these two branches.

05
UNEXPLAINED
Forget entries; keep handles and callers.
↗

Both lifecycle calls empty every handle synchronously and can repeat. Handles remain registered and reusable, even while project release waits. Caller-held promises are not cancelled; a late old settlement cannot replace a new entry. There is no close or deregistration API.

Reason: No specific reason was found for this reusable, non-closing API or its retained handle registry.

06
STATED
Start a turn after refresh succeeds.
↗

Backend refresh keeps the prior cache turn if refresh fails; this is not a rollback of all refresh work. Source refresh, any workspace project refresh, and state refresh precede beginTurn. Success clears caches even with unchanged files. This ordering already exists in base.

Reason: The PR says a failed refresh must preserve the current successful turn.

07
STATED
Empty before awaiting cleanup.
↗

Release clears semantic entries immediately in both versions, before calling project cleanup. A pending or failed cleanup leaves old entries absent. A query can refill a handle during that wait; clearing is not a lock.

Reason: The PR says released semantics must be unavailable while release is pending or rejecting.

08
UNEXPLAINED
Make backend release wait and propagate failure.
↗

The service changes void → Promise<void>; backend release now awaits it. In a held-cleanup run, base fulfills early while head stays pending; a cleanup rejection reaches head’s caller. The PR declares this barrier but does not reconcile it with its failure-preservation claim or the spec’s unchanged-lifecycle rule.

Reason: The barrier is declared. A reason for changing this caller-visible release outcome, within the parity promise, was not found.

09
UNEXPLAINED
Keep fresh projections over cached locations.
↗

References and callers share the internal reference-location search, but public findReferences reprojects on each access. Position queries cache locations, including empty results, then rehydrate nodes each time. Fresh arrays can contain the same nodes; backend async wrappers need not preserve service promise identity.

Reason: The PR preserves these behaviors; no specific reason for the existing projection boundaries was found.

10
UNEXPLAINED
Choose composition and a small public API.
↗

Core exports TurnScopedCacheScope plus a getOrCreate-only handle interface. Each service constructs its scope rather than extending a cache base. beginTurn now accepts readonly WorkspaceFile[] instead of a whole WorkspaceSnapshot; the array is retained by reference.

Reason: The precise export shape, composition choice, and narrower argument have no specific reason in the inspected PR, commits, or spec. The spec describes shared backend bases.

11
UNEXPLAINED
Add characterization; preserve the old tests.
↗

Six service cases and four core cases add identity, projection, failure, refresh, release, and generic-cache checks. All five old cases and helpers are byte-identical; no assertions are removed or weakened. The new release test covers pending/rejection, without an explicit successful deferred-release check; this experiment records both outcomes. Focused checks do not establish full command parity.

Reason: The commits record characterization and lifecycle intent. They do not explain the exact selection of cases or the missing successful deferred-release assertion.

12
STATED
Keep the surrounding cleanup machinery.
↗

This six-file PR leaves project cleanup, query algorithms, daemon/worker topology, and transport in place. Concrete TypeScript project cleanup is synchronous; the graph can await projects in sequence. The bench injects a long pending graph promise to expose the release contract, not a measured production delay.

Reason: The PR confines its move to cache lifetime while preserving the existing algorithms; the spec keeps language-specific work in the backend.
