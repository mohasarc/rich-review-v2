D01stated

Move the clearing job into core ↘

TypeScript keeps algorithms, keys, projections, and its file list. Core implements and exports the scope and handle type. Each service owns its own scope instance; the existing package dependency and process boundary stay put.

The architecture spec assigns shareable cache lifetime to core and semantic query bodies to TypeScript.

Keep six independent stores ↘

One scope coordinates six separate Maps. Five store promises by symbol identity; the position store keeps location arrays by file and offset. Callers and references still share reference discovery.

The PR chooses six handles because the existing key and value spaces are independent.

D04stated

Preserve entries, distinguish their projections ↘

Cache hits return the exact value, including empty results. Four direct service query methods reuse promises. Reference results and node arrays are rebuilt; backend async wrappers need not reuse the cache's promise. Miss observers still count the underlying searches.

The PR explicitly preserves all six algorithms, keys, and promise/value identities. The original rationale for reprojection is not supplied.

Reason & evidence ↗
D05stated

Treat undefined as a present entry ↘

The generic handle uses Map.has before Map.get. Its factory can return undefined once and still get a cache hit. The six TypeScript stores already hold truthy promises or arrays; this is a broader generic contract.

The PR names undefined as a valid cached value.

Reason & evidence ↗
D06stated

Keep rejected promises; retry synchronous throws ↘

A returned promise is stored even if it rejects. A factory throw inserts nothing. Clearing cancels neither an old promise nor its result; later settlement cannot overwrite a new entry because the scope installs no settlement callback.

Preserving existing query failure behavior and value identity is the PR's stated constraint, not a new retry policy.

Reason & evidence ↗
D07stated

Begin the next turn after refresh succeeds ↘

Both revisions clear after source, applicable project, and workspace-state refresh succeeds—even with unchanged files. Failure skips the file-list handoff and clear. A command returning is not a clearing signal. This is a cache guarantee, not rollback of all earlier refresh effects.

The PR says failed refresh must preserve the current successful turn.

Reason & evidence ↗
D08stated

Empty entries before starting project cleanup ↘

Clearing remains synchronous and comes first in both revisions. The unchanged graph releases projects in order and can stop on rejection; concrete TypeScript project cleanup is synchronous, even though its graph returns a promise.

Old cached semantics must be unavailable while project release is pending or rejecting, according to the PR.

Reason & evidence ↗

The new service and backend await graph cleanup. A held graph leaves backend release pending; rejection reaches that caller. The PR explicitly declares this barrier. How this change fits the plan's unchanged timing/failure promise is unrecorded.
