1# Symnav Daemon Functional Spec23## Goal45Symnav keeps a reusable workspace daemon so repeated navigation commands avoid rebuilding the same project state. Ordinary commands never wait for daemon startup: they answer locally while one daemon warms in the background, then later commands switch to the ready daemon. This must remain useful on representative workspaces and on projects up to ten times larger. The daemon is not a language server, a network service, or a new navigation surface. This spec defines product behavior only and avoids implementation choices.67## Primary User89The first-class user is a coding agent issuing many symnav commands during a long development session.1011Its default experience is:1213- First command starts one background warm-up and answers locally.14- Further commands answer locally while warm-up continues.15- Commands use the daemon after it becomes ready.16- No navigation output reveals which route answered it.1718Explicit alternatives are `symnav daemon start|status|stop` for lifecycle control and `SYMNAV_DAEMON=0` for fully local execution.1920## Core Guarantees2122### Ordinary commands never wait for warm-up2324An ordinary command starts local execution without waiting for a daemon to become ready.2526```text27If no ready daemon exists when a command is accepted, that command answers locally while one daemon warms independently.28```2930The route chosen when a command is accepted does not change midway through that command. A daemon becoming ready does not cancel or duplicate local work already in progress.3132Examples:3334- First `resolve` in a large workspace starts warm-up and runs locally at once.35- A second `overview` issued ten minutes into a twenty-minute warm-up also runs locally at once.36- First command after readiness uses the daemon.37- A warm-up failure does not delay or alter local command output.3839There is no flag that makes ordinary navigation commands wait for warm-up.4041### One durable warm-up per workspace4243Concurrent callers share one warm-up. Initiating caller does not own daemon lifetime.4445```text46For one workspace and state location, at most one daemon is starting or ready, regardless of caller count or caller lifetime.47```4849The daemon continues warming after initiating command exits. Later callers observe or adopt that warm-up; they do not restart it. A caller failure, timeout, or disconnect cannot stop a healthy warm-up.5051Examples:5253- Ten commands begin together in a cold workspace. All ten answer locally and exactly one daemon warms.54- Initiating process exits one second after launch. Warm-up continues to readiness.55- A healthy warm-up takes twenty minutes. It is not discarded because of project size or elapsed time.56- Warm-up process exits. Starting state is cleared promptly and a later eligible command may try again.5758There is no healthy-startup timeout override because healthy automatic warm-up has no project-size deadline.5960### Warm answers equal local answers6162A command answered by the daemon produces the same stdout, stderr, and exit code as the same command run locally against the same workspace state.6364```text65For any command, arguments, cwd, and workspace contents:66output(daemon) == output(local), byte for byte, including exit code.67```6869Warnings, errors, `--help`, `--version`, and `--json` are covered. There is no daemon-only navigation output and no local-only navigation output.7071There is no parity override.7273### Answers reflect current workspace state7475Every request sees workspace contents current when its execution turn begins.7677```text78A request never answers from workspace state older than start of its execution turn.79```8081For local commands, execution turn begins when local execution starts. For queued daemon commands, it begins when command reaches front of queue.8283Examples:8485- A file edited after one request is reflected in next request.86- A queued request sees edits completed before its queue turn begins.87- Added, deleted, and renamed files appear in next answer.8889There is no stale-data override.9091### Nested Git workspaces are separate boundaries9293Selected workspace is nearest Git workspace containing caller. A descendant directory with its own Git workspace marker belongs to a separate workspace.9495```text96Parent commands never traverse, index, refresh, or return files from a nested repository, worktree, or submodule.97```9899This boundary is independent of ignore rules. Ignore negation cannot pull a nested workspace back into its parent.100101Examples:102103- A parent repository containing `.worktrees/feature` does not return symbols from that worktree.104- Running with `--cwd .worktrees/feature` selects and navigates worktree normally.105- Directly targeting a nested-workspace file from its parent fails with guidance to select nested workspace.106- A directory named `.worktrees` with no nested Git workspace remains ordinary workspace content.107108There is no include-nested-workspaces override.109110### Slow or busy does not mean dead111112Long startup, queue wait, and command execution are not daemon failures.113114```text115Only authenticated evidence of process exit, protocol incompatibility, or corrupt communication invalidates daemon ownership.116```117118A caller timeout or disconnect does not remove a live daemon record, stop a healthy daemon, or replay accepted work locally. A short command queued behind long work cannot destroy daemon state.119120Lifecycle status remains responsive while navigation work is running and reports daemon as busy rather than absent.121122There is no force-invalidate-on-timeout override.123124### Resource failures are controlled125126Supported workloads do not end with raw out-of-memory output, partial responses, or an unreported daemon disappearance.127128```text129A resource or response-size limit produces either a complete normal answer or a complete symnav error while preserving recoverable daemon state.130```131132Known capacity failures are not immediately repeated through equivalent local execution. A large response does not by itself mark daemon corrupt.133134There is no raw-failure override.135136## Scope137138### Included139140- Background warm-up for `overview`, `resolve`, `def`, `refs`, `context`, `graph`, and `stats`.141- Local answers during warm-up.142- One durable starting or ready daemon per workspace and state location.143- Startup that may take at least twenty minutes without a healthy-startup deadline.144- Warm execution with byte-for-byte local parity.145- Current-state refresh before each command's execution turn.146- Nested repository, worktree, and submodule boundaries.147- FIFO navigation execution within one ready workspace daemon.148- Responsive lifecycle control during navigation work.149- Controlled handling of long commands, caller disconnects, resource pressure, and large responses.150- Explicit `daemon start`, `daemon status`, and `daemon stop`.151- `SYMNAV_DAEMON=0` local-only execution.152- State-location isolation through `SYMNAV_STATE_DIR`.153- Version mismatch replacement.154- Diagnostic logs and execution-mode telemetry.155- Gating performance and resource measurements on realistic and scaled workspaces.156157### Excluded158159- Concurrent navigation execution within one workspace daemon.160- Cross-workspace shared project state.161- Traversing nested Git workspaces from a parent command.162- A network-reachable daemon or third-party protocol.163- Persisting a loaded workspace across daemon restarts.164- A user flag for startup timeout, request timeout, idle timeout, or memory limit.165- New navigation commands or changes to navigation result grammar.166- File-watcher configuration exposed to users.167- Support for non-TypeScript language backends beyond existing participation contract.168169## Interaction Model170171### Ordinary commands172173Existing invocations are unchanged:174175```console176$ symnav resolve PaymentProcessor177$ symnav overview src/checkout/CheckoutService.ts178$ symnav refs CheckoutService::processPayment179```180181`--cwd <dir>` selects both workspace and daemon. A command never accepts a daemon name, process identifier, endpoint, or nested-workspace inclusion flag.182183### Daemon commands184185```console186$ symnav daemon start187$ symnav daemon status188$ symnav daemon stop189```190191`start` and `stop` act on workspace selected by current directory or `--cwd`. `status` lists validated daemon state for current user and configured state location. All three accept `--json`.192193### Local-only execution194195```console196$ SYMNAV_DAEMON=0 symnav refs CheckoutService::processPayment197```198199No daemon is contacted or started. Output remains equivalent to warm execution.200201### State-location isolation202203```console204$ SYMNAV_STATE_DIR=/tmp/session-a symnav resolve PaymentProcessor205```206207Registry, logs, endpoints, and daemon ownership are isolated from clients using another state location. Separate state locations do not collide or invalidate each other's daemons.208209## Output Format210211Navigation output is unchanged.212213### `daemon start`214215Ready:216217```console218$ symnav daemon start219Daemon ready for /Users/mo/projects/reelcut2202142 files loaded in 9.8s221```222223Already running:224225```console226$ symnav daemon start227Daemon already running for /Users/mo/projects/reelcut (pid 48213, up 14m)228```229230An explicit start waits until readiness or a confirmed startup failure. A healthy twenty-minute startup remains attached and produces no progress bytes before its final response.231232### `daemon status`233234Ready daemons:235236```console237$ symnav daemon /Users/mo/projects/reelcut270```271272Both cases exit `0`.273274### Controlled capacity failure275276```text277Cannot answer: workspace operation exceeded available resources.278```279280Error is complete, uses normal symnav error output, and does not include a runtime crash dump.281282## Cross-cutting Concerns283284### Routing and queueing285286Routing is decided once per command:287288| State when command is accepted | Behavior                                                      |289| ------------------------------ | ------------------------------------------------------------- |290| No daemon                      | Trigger one background warm-up and execute locally            |291| Starting                       | Execute locally without waiting or starting another daemon    |292| Ready and idle                 | Execute through daemon                                        |293| Ready and busy                 | Queue through daemon in arrival order                         |294| Confirmed dead or incompatible | Clear invalid ownership, trigger replacement, execute locally |295296Lifecycle requests remain independent of navigation queue responsiveness.297298### Lifetime299300- Idle exit: `30 minutes` after last completed navigation request.301- Warm-up time does not count as idle time.302- Navigation activity resets idle period.303- Workspace deletion, explicit stop, confirmed incompatibility, or controlled resource shutdown may end daemon sooner.304- Initiating and waiting caller lifetimes do not control daemon lifetime.305306### Performance targets307308Targets are measured end to end on a representative worktree of about 4,000 TypeScript files after daemon readiness:309310```text311Targeted overview:        under 500 ms312Resolve and def:          under 2 s313Refs, context, and graph: under 5 s for representative depth-one queries314```315316Warm no-change performance is measured repeatedly, not from one best run. Targets include freshness, command work, rendering, and transport, but exclude queue wait.317318Scale gates cover realistic workspaces at `1x`, `2x`, `3x`, and `10x` reference-workspace size. Every gate records startup duration, command duration, queue wait, peak memory, response size, result parity, freshness after changes, and daemon continuity.319320A scale gate may take longer as project size grows. Representative commands at every scale complete under default resource policy. A gate does not pass if daemon restarts, disappears from status, emits raw resource failures, or retries accepted work locally.321322### Diagnostics323324Daemon diagnostics record:325326- Startup duration and outcome.327- Queue depth and queue-wait duration.328- Current command and elapsed time.329- Workspace discovery and freshness duration.330- Navigation and rendering duration.331- Response size.332- Current and peak memory.333- Controlled shutdown and confirmed crash reason.334335Diagnostics never appear in navigation stdout or stderr.336337### Telemetry338339Execution mode remains `warm`, `cold`, or `fallback`.340341- Local commands during healthy warm-up are `cold`.342- Commands replayed locally after a pre-acceptance daemon failure are `fallback`.343- A command accepted by daemon is recorded once and is not also recorded as fallback because caller disconnected.344- `SYMNAV_TELEMETRY=0` disables telemetry in every mode.345346### Platforms347348Behavior applies on macOS, Linux, and Windows. Warm and local parity runs on supported CI platforms.349350## Transparent Background Warm-up351352**Purpose.** Build reusable project state without making ordinary commands wait.353354**Produces.** One local answer per command until daemon is ready, then warm answers.355356**Does not produce.** Startup banners, progress output, duplicate daemons, duplicate command answers, or partial output.357358Example:359360```console361$ symnav resolve PaymentProcessor      # local answer; warm-up starts362$ symnav overview src/orders.ts        # local answer; same warm-up continues363$ symnav def PaymentProcessor::charge  # warm answer after daemon becomes ready364```365366**Defaults.** Enabled.367368**Edge cases.** Concurrent first calls elect one warm-up. Caller exit does not cancel it. Confirmed startup failure clears starting state so a future call may retry.369370## Explicit Daemon Start371372**Purpose.** Wait for a workspace to become warm before beginning a navigation session.373374**Produces.** One readiness or already-running response.375376**Does not produce.** Navigation output or a healthy-startup timeout.377378**Edge cases.** Concurrent explicit starts wait for same daemon. A child failure returns promptly. `SYMNAV_DAEMON=0` prints `Daemon disabled by SYMNAV_DAEMON=0` and exits `1`.379380## Daemon Status381382**Purpose.** Show starting, ready, busy, and queued work without disturbing it.383384**Produces.** Workspace, state, process identifier, uptime or startup elapsed time, file count when known, memory, current command when busy, queue depth, and last-request age.385386**Does not produce.** False absence because a command blocks navigation work, records from another state location, or data about another user.387388**Defaults.** Workspace-path sort order. Status response target: `1 second`.389390**Edge cases.** Confirmed stale records are removed. An unresponsive but live process is reported as unresponsive, not silently omitted. Status never invalidates a daemon.391392## Daemon Stop393394**Purpose.** End background work and release memory explicitly.395396**Produces.** Stopped, killed, or absent confirmation.397398**Does not produce.** An error for an absent daemon.399400**Defaults.** Graceful wait: `5 seconds`, then controlled termination.401402**Edge cases.** An in-flight request may complete during graceful wait. Forced stop produces one complete outcome for its connected caller and removes daemon ownership after process exit.403404## Warm Navigation405406**Purpose.** Reuse loaded workspace state for repeated commands.407408**Produces.** Current, byte-equivalent navigation answers within scale targets.409410**Does not produce.** Results from nested workspaces, stale results, raw resource failures, or full repeated local work after caller timeout.411412**Edge cases.** Long results transfer completely or fail with a controlled result-size error without invalidating daemon. Package aliases and workspace imports resolve with same correctness as local project execution. Empty reference, context, or graph results mean there are no results, not that workspace imports were skipped.413414## Summary415416- Ordinary commands answer locally while one daemon warms independently.417- Healthy warm-up may take twenty minutes or more without being discarded.418- Exactly one daemon starts per workspace and state location.419- Ready commands are current and byte-equivalent to local execution.420- Nested Git workspaces never leak into parent results.421- Slow, queued, and disconnected callers do not invalidate healthy daemon state.422- Status stays truthful and responsive during long work.423- Resource and response-size failures are controlled and never blindly replayed.424- Realistic 1x, 2x, 3x, and 10x reference-workspace gates cover latency, memory, parity, freshness, and continuity.
