   1 <!--
   2 PURPOSE
   3 
   4 A reviewer reads this description, then walks the commits one-by-one.
   5 The description's job is to load them with just enough context to
   6 spot HIGH-LEVERAGE issues (wrong interface, wrong abstraction, wrong
   7 approach) BEFORE deep-reading any function body. It is not a tour,
   8 not a narrative, not a re-statement of the diff.
   9 
  10 The mental model is a whiteboard. A smart coworker explaining the
  11 change sketches the old shape, redraws what changed, writes the new
  12 method names, notes a decision in the corner, and circles the
  13 hairiest spot. Then they hand you the marker. That is the target —
  14 the shape of a 60-second standup at a board, not a paragraph.
  15 
  16 Goal: scannable in 30 seconds. The reviewer must be able to flag a
  17 wrong decision without reading a single function body.
  18 
  19 SKIP-IF-EMPTY (the load-bearing rule)
  20 
  21 An empty or padded section is worse than no section. If a section's
  22 content would be vague, generic, or a restatement of the title /
  23 diff / commits, DELETE THE ENTIRE SECTION — heading and all. The
  24 order below is fixed; sections you skip simply do not appear.
  25 
  26 Do not pad. Do not add a section to look thorough. Do not add
  27 "Summary", "What changed", "Overview", or "Generated by" sections.
  28 The title is the summary; commits are the changelog; tools do not
  29 need credit.
  30 
  31 SIZE AS SIGNAL
  32 
  33 More than 5 entries under Decisions, or more than ~10 lines of code
  34 under Public surface, is evidence the PR is too big. Pause and
  35 consider splitting before continuing.
  36 
  37 WRITING
  38 
  39 Concise. One concrete fact per sentence or bullet. No metaphors,
  40 no "really" / "very" / "simply" / "just", no decorative adjectives.
  41 Concrete nouns over hand-waving ("validates input order" not
  42 "improves robustness").
  43 
  44 GUIDANCE COMMENTS
  45 
  46 The HTML comments under each heading explain when to include the
  47 section and the shape its contents should take. After filling a
  48 section, you may leave the guidance comment in place (it renders
  49 invisibly on GitHub) or remove it.
  50 -->

  67 ## Shape
  68 
  69 <!--
  70 Old → new at the STRUCTURAL level: where code lives, what owns what,
  71 how runtime flow moves. Not behavior, not implementation detail.
  72 
  73 Skip the section if there is no architectural delta (pure bugfix,
  74 small rename, docs-only).
  75 
  76 Form — default to a paired before/after diagram. Skip the diagram
  77 only when the change is genuinely small (pure rename, single-file
  78 bugfix, docs-only, mechanical type fix); in that case 3-5 bullets
  79 are enough. When in doubt, draw the diagram.
  80 
  81 Diagram rules:
  82   - PAIRED before/after — two diagrams, one labeled "Before", one
  83     labeled "After". Never a standalone "new shape"; the delta is
  84     the point.
  85   - COLOR-CODED to show what changed vs. what was already there:
  86       green fill  = added in this PR
  87       red fill    = removed in this PR
  88       yellow fill = changed in this PR
  89       default     = pre-existing, unchanged
  90     Include a one-line legend under the diagrams.
  91   - ANNOTATIONS on arrows and nodes — name the load-bearing
  92     relationships ("injected by caller", "returns", "extends",
  93     "<<unexported>>"). Bare class boxes do not earn their place.
  94   - Mermaid for general use; ASCII for tiny shapes (≤4 nodes).
  95   - ≤8 nodes per diagram. If you need more, either the PR or the
  96     diagram is wrong.
  97   - One verb per arrow type ("uses" / "depends on" / "calls" —
  98     pick one).
  99   - Each diagram captioned with the delta it shows.
 100   - No nested subgraphs beyond one level. No general-architecture
 101     portraits unrelated to this PR's change.
 102 
 103 A short prose lead-in (1-3 bullets) under the diagrams is welcome
 104 when the picture alone leaves something implicit.
 105 -->

 107 ## Where it lives

 109 <!--
 110 Repo-root file-structure sketch for the important changed areas.
 111 This is placement review, not a complete file list.
 112 
 113 Include when changes span multiple packages/directories, add/remove/
 114 move files, or introduce a new ownership boundary.
 115 
 116 Skip for single-file fixes, obvious small renames, docs-only edits,
 117 or when paths add no review signal.
 118 
 119 Form: a Change Tree — a Unicode filesystem tree in a ```text block,
 120 anchored at repo root. Use `.` as the root. Include unchanged parent
 121 directories as context; annotate only nodes that matter for
 122 ownership or review.
 123 
 124 Legend: `++` added, `**` changed, `~~` moved, `--` removed.
 125 
 126 Example (illustrative paths):
 127 
 128   .
 129   └── src/
 130       ├── ** payment-form.ts             # wires retry flag
 131       ├── ++ invoice-retry/
 132       │   └── ++ ... 12 files            # owns retry scheduling
 133       └── ~~ receipts/
 134           └── ~~ ... 3 files             # moved from src/billing/
 135 
 136 Rules:
 137   - Show important changed areas, not every touched file.
 138   - Use `... N files` for collapsed groups. Count files, even when
 139     the group is generated or mechanical.
 140   - Place `~~` moved entries at their new path and note the old path:
 141     `# moved from <old path>`.
 142   - Use `**` only for changed existing files whose placement or role
 143     matters.
 144   - Include tests only when their placement carries review signal.
 145     Collapse colocated tests into the source group when they follow
 146     the same ownership.
 147   - Inline `# ...` comments should name purpose or ownership. Do not
 148     restate marker status except the required moved-from note.
 149 -->

 153 <!--
 154 Verbatim signatures of new / changed / removed exports. Code, not
 155 English. The reviewer reads code faster than prose and can flag a

 157 
 158 Skip the section if the PR adds or changes no public surface.

 173 
 174 More than ~10 lines here is a size-signal — the PR is probably too
 175 big to review in one sitting.

 178 ## Decisions
 179 
 180 <!--
 181 ≤5 entries. Each is a load-bearing judgment call — an interface
 182 choice, an abstraction choice, an approach choice, a placement
 183 choice. The kind of thing where if the reviewer disagrees, the PR
 184 needs to change shape, not just nits.
 185 
 186 Form, one per entry:
 187     Chose X over Y, because Z.
 188 
 189 The alternative Y must be one you ACTUALLY CONSIDERED. If you cannot
 190 name a real alternative, the decision was not load-bearing — do not
 191 list it.
 192 
 193 Omit the entire section when no decisions meet that bar. This is
 194 common for bugfixes, renames, and mechanical refactors.
 195 
 196 Bad:  "Chose to use a class."
 197       (No alternative named.)
 198 Good: "Chose a class with constructor injection over a module-level
 199       singleton, because tests need to swap in a fake without
 200       monkey-patching."
 201 
 202 More than 5 real decisions is a size-signal — split the PR.
 203 -->
