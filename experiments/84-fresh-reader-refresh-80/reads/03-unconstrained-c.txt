WHAT THIS CHANGE ASKS THE HUMAN TO UNDERSTAND
The decisions, including the small ones.
Read them in order →
01
Two implementations coexist

The package owns the new composition. The CLI continues through its existing graph.

CHOICE 01
STATED
↗
Stage the package; leave the CLI connected to its copies

The new client and mechanisms exist alongside 38 frozen CLI production files. This PR does not switch the shipped CLI to DaemonClient.

PR body: ownership relocation and host invocation coordination need separate review boundaries.

CHOICE 02
STATED
↗
Freeze paths and source bytes, normalizing CRLF

A fixed SHA-256 digest and a count of 38 protect the compatibility set. CRLF becomes LF; other source changes still change the digest.

Commit “Specify portable daemon compatibility hashing” records portability; the test explicitly exercises CRLF and a changed source.

CHOICE 03
STATED
↗
Give private mechanisms ten directory owners

Ten owner directories place mechanisms in a daemon package with no other internal production dependency. The completion spool gets a package-local record codec instead of importing the CLI output utility.

Architecture spec: give daemon policy and mechanism one home; daemon must not depend on navigation or CLI implementation.

CHOICE 04
STATED
↗
Make process and worker entries executable package subpaths

The manifest exposes process-entry and worker-entry as side-effect-only entries. Launcher and worker resolve those files relative to package modules.

Architecture spec names real process and worker entries as part of daemon package extraction; commits explicitly require exhaustive entry exports.

02
A host hands over execution

Syntax and product knowledge stay with the host; daemon decisions sit behind a client.

CHOICE 05
STATED
↗
Pass product knowledge in; return bytes and reports

The host supplies state path, version, enabled flag, executor factory, executor module URL, readiness probe and optional policy. Each execute call supplies workspace, command, argv, cwd and telemetry flag.

Architecture spec: the daemon moves bytes for an injected executor and must not know navigation internals or parse CLI syntax.

CHOICE 06
STATED
↗
Keep Node out of public declarations

The public façade describes a small runtime port and dynamically imports the Node-backed implementation. The façade’s declarations do not pull Node ambient types into hosts.

PR body: host declarations must not acquire Node ambient dependencies.

CHOICE 07
UNEXPLAINED
↗
Begin loading at construction; retain one runtime promise

Constructing DaemonClient starts the dynamic load immediately. Execute and control await the same promise; a rejected load is not retried by these methods.

The declaration-isolation reason is stated. No separate reason was found for starting in the constructor or retaining a rejected promise.

CHOICE 08
STATED
↗
Reuse lifecycle composition and keep action-specific results

Start/status/stop have precise overloads. Status gets a separate response timeout; disabled blocks start and sends execute locally, while status and stop still run. Control errors propagate.

The architecture specifies lifecycle reports; the policy distinguishes status response timing. The client’s lifecycle tests state the disabled and failure behavior.

CHOICE 09
STATED
↗
Let the host name the readiness execution

The client passes a host-supplied command and argv to startup. Readiness still executes with cold mode and telemetry off; the internal coordinator retains a --version default.

The architecture keeps CLI syntax with the host; commits explicitly specify a host-owned readiness probe. Control-plane-only readiness remains a deferred behavior.

03
A decision ends the search

Short-circuit routing and retry authority determine which side effects happen.

CHOICE 10
STATED
↗
Stop after the first routing decision

Record present → not starting → version compatible → responsive. Read once and observe at most once. A starting record wins even when its version is old.

PR body: the first routing decision must prevent every later side effect. Architecture spec makes the order explicit and independently testable.

CHOICE 11
STATED
↗
Run cold work now; trigger only selected warm-ups

Disabled, starting and recovery execute cold. Absence executes cold plus an independent trigger; dead/incompatible execute fallback plus a trigger. Every local attempt gets a fresh executor with no resource sampler.

The architecture preserves routing and local execution behavior. Existing CLI routing and new client characterization both express independent warm-up.

CHOICE 12
STATED
↗
Let retry-safety authorize local re-execution

Only a DaemonTransportError marked retrySafe permits local fallback. Submitted uncertainty, accepted failures and malformed warm completions return controlled warm failures; they do not replay.

PR body: replay safety belongs to the daemon client. The architecture keeps one owner for the retry-safety decision.

CHOICE 13
STATED
↗
Own result capture, controlled output and cleanup inside the package

The client creates capture from output policy, spilling to the OS temporary directory, and constructs failure output itself. A private capture factory port stays internal; callers consume and dispose the returned output.

PR body: warm transfer cleanup and replay safety belong to the client, rather than host-provided storage or output factories.

CHOICE 14
STATED
↗
Dispose a malformed warm result before replacing it

A non-integer exit code or missing output becomes an incomplete-request result. The package client attempts disposal of available malformed output; the CLI dispatcher’s older check does not.

PR body assigns warm transfer cleanup to the client; the new test explicitly requires disposal before returning the controlled result.

04
Ownership becomes explicit

Clock, startup credentials, coordinates and request authentication keep their own boundaries.

CHOICE 15
STATED
↗
Use the daemon’s wall and monotonic clock everywhere it was threaded

Wall time drives lifetime, registry leases, controller waits, ledger timestamps and replacement windows. Monotonic time drives queue/worker durations; the queue’s standalone default changes to monotonic.

Architecture spec assigns wall and monotonic clock ownership to the daemon; PR retains existing lifetime behavior.

CHOICE 16
STATED
↗
Keep construction/acceptance-based idle timing; defer two changes

The deadline starts at construction and resets on navigation acceptance. Completion only checks it; readiness does not reset it. Readiness-armed and completion-based timing are added to the follow-up spec.

PR body: changing lifetime behavior is explicitly deferred rather than folded into extraction.

CHOICE 17
STATED
↗
Make registry ownership matching canonical, with narrow and exact expectations

Callers delegate startup equality and cleanup to the registry. Every match checks identity and instance; supplied token, kind, PID, timestamps and revision narrow the match. Full observed owners are compared exactly.

Architecture spec requires one owner for lock-ownership checks; commits separately specify canonical authority and narrow coordinates.

CHOICE 18
UNEXPLAINED
↗
Let the process coordinator adopt and validate launch coordinates

WorkspaceDaemon becomes DaemonProcessCoordinator. It receives the complete coordinate object and required clock, validates identity/endpoint, and uses that endpoint for listening. Callback wiring keeps execution, delivery, worker and resource owners separate.

The spec names the process-coordinator split. No explicit reason was found for moving coordinate validation from entry to constructor or the detailed construction API choices.

CHOICE 19
UNEXPLAINED
↗
Characterize the existing authentication order and its exceptions

Identify/terminate/kill check instance+token. Other messages first check protocol+instance; execute and result operations add token checks. Ping and stop keep only protocol+instance authentication.

New tests explicitly preserve these different envelopes. No reason for the asymmetry or the order was found in the supplied rationale sources.

05
The evidence changes owners too

Moving a test and preserving everything it observed are separate choices.

CHOICE 20
STATED
↗
Move 37 mechanism test files and give them generic fixtures

Mechanism tests move from CLI to package. Generic executors, canonical-path/output helpers and duplicated policy helpers remove CLI implementation imports. tsx is added as a daemon development dependency.

Architecture spec: tests importing mechanisms move into the package or use its public surface; commit “Keep executor fixture package-independent” states the fixture boundary.

CHOICE 21
UNEXPLAINED
↗
Narrow worker tests’ observation of the real CLI executor

The integrated CLI version-mismatch case disappears; a direct CLI factory rejection test is added. The readiness case uses a generic executor and removes startup/result timing expectations.

Package-independent fixtures have a stated reason. No reason was found for losing these specific timing assertions or changing mismatch coverage from worker classification to factory rejection.

CHOICE 22
UNEXPLAINED
↗
Delete CLI entry tests; add built package entry evidence

Two app entry tests are removed. New package boundary, export and built-process/worker tests exercise package ownership, startup configuration and failure cleanup. Windows and other-platform cleanup expectations differ.

Real package entries are explicitly requested. No equivalence argument was found for removing the app-entry assertions; the Windows branch is specified by a commit, without explanatory body.

CHOICE 23
UNEXPLAINED
↗
Retire policy-testing and redraw source guard coverage

The policy-testing export and its lint restriction/tests disappear; helpers move into both test trees. Exact root/entry export checks remain. A new raw-clock scan examines only lifecycle siblings, not all daemon directories.

The old export was labeled temporary, but no explicit removal rationale or reason for the local scope of the new clock scan was found.

CHOICE 24
UNEXPLAINED
↗
Run daemon package test files serially

A new Vitest configuration sets fileParallelism to false. This changes how this package’s test files are scheduled.

Not named in the PR’s stated intent. No scheduling reason was found in the PR body, commit messages or inspected specifications.
