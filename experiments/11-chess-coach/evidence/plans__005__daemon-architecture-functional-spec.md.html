1# Symnav Daemon Architecture Functional Spec23## Goal45Restructure the merged daemon work so each concern lives in the package that owns it: a self-contained daemon package that knows nothing about symbols, a core that knows nothing about daemons, a TypeScript backend that holds only TypeScript-specific logic, and a CLI app that only composes. The daemon's user-facing behavior is defined in `daemon-functional-spec.md` and does not change. This is refactor work: not a rewrite of the daemon, not a change to any command's output or timing, and not a new language backend. This spec defines product behavior for contributors and hosts of the packages; implementation choices live in the phased plans.67## Primary User89**Contributors** changing symnav. Their default experience: a package boundary tells them where a concern belongs, and the build refuses an import that crosses the locked dependency graph.1011**Hosts** composing the packages into a runnable product. The CLI app is the first host. A future host (editor extension, MCP server, benchmark harness) composes the same packages the same way. No host reaches into another package's internals.1213End users of the `symnav` binary observe no change from this work.1415## Core Guarantees1617### Behavior is unchanged1819This is a refactor. Every command, daemon lifecycle action, diagnostic record, telemetry event, and failure path behaves as it does today.2021```text22Given the same workspace, arguments, environment, and daemon state, output bytes,23exit code, execution mode, and lifecycle outcome are identical before and after.24```2526Correct: a restructuring change passes the existing e2e parity and daemon suites without touching a single expectation. Incorrect: a restructuring change "fixes" a queue, eviction, timeout, or path while moving code.2728There is no "it was obviously a bug" override. Behavior defects found during restructuring are recorded in `daemon-follow-ups-functional-spec.md` and changed separately.2930### The daemon package depends on nothing internal3132The daemon package imports no other symnav package. It moves bytes for an executor it is handed; it does not know what a symbol, workspace snapshot, or backend is.3334```text35@symnav/daemon may import: (nothing internal)36```3738Correct: the daemon logs a worker's refresh counters as an opaque diagnostics record supplied by the executor. Incorrect: the daemon's protocol names a core type to describe those counters.3940There is no exception for "just a type".4142### Core knows nothing about daemons or processes4344Core answers questions about a workspace and its symbols. It has no concept of a background process, socket, registry, warm-up, or route. Retaining state across requests means keeping a core object alive; core does not ask its host how to persist anything.4546```text47Core has no persistence port, no daemon port, and no notion of warm vs cold.48Warm = the same session object answers again. Cold = a new session object.49```5051There is no persistence abstraction until a second consumer of one exists.5253### A language backend holds only language-specific logic5455A concept that another language could share lives in core as a base the backend extends. The backend supplies only what depends on the language's toolchain.5657```text58Shared in core: file revision tracking, prepared-file index, declarations-by-identity,59transactional index publication, project-membership graph with input invalidation,60turn-scoped query cache lifecycle.61TypeScript-only: extraction from TypeScript syntax trees, tsconfig parsing (extends,62references, path aliases, include/exclude), program and language-service creation,63semantic query bodies.64```6566### The CLI app is composition only6768`apps/cli` parses command-line syntax, resolves environment (state directory, daemon enabled), creates concrete dependencies, wires packages together, and prints. It holds no daemon policy, no workspace policy, and no navigation logic.6970```text71A decision about routing, admission, ownership, delivery, memory, or lifetime that72lives in apps/cli is a defect.73```7475### Every threshold has one owner and a recorded reason7677Numeric limits (memory caps, spool caps, deadlines, idle timeout, probe timeout, trace retention, replacement circuit, reattachment attempts) live in one policy object inside the daemon package, each with a stated reason in a policy record under `plans/`. Tests override the policy object; users cannot.7879```text80No CLI flag, environment variable, or config file tunes a daemon threshold.81```8283This restates the no-tuning rule from `daemon-functional-spec.md`; it is not relaxed here.8485## Scope8687### Included8889- New `@symnav/daemon` package owning entry points, process launch, election, registry, transport, worker threads, admission, queueing, delivery, spooling, resource supervision, lifetime, diagnostics, and its own clock.90- Executor contract defined by the daemon package; CLI implements it.91- Executor reaches the daemon's worker as an injected module location, dynamically loaded.92- CLI keeps argv classification and hands the daemon client a workspace root plus argv.93- Core `WorkspaceSession` replacing the CLI's request-scope factory.94- Core revisioned-backend base, project-graph base, turn-scoped cache; TypeScript backend extends them. `WorkspaceSourceCache` moves to core.95- State-directory resolution moves from telemetry to the CLI; telemetry and daemon receive a path.96- Daemon lifecycle rendering moves to `@symnav/renderer`.97- Admission and client routing restructured as ordered guard lists with one closed rejection vocabulary.98- `WorkspaceDaemon` split into process coordinator, accepted-execution session, delivery session, worker-generation manager, activity projector.99- `LocalDaemonTransport` split into codec/validator, lifecycle client, execution client, result receiver, socket client, socket server.100- One owner each for command-name vocabulary, lock-ownership check, retry-safety decision, and `DaemonExecutionFailureCode` (worker variant renamed).101- Dependency table, ESLint boundaries, project references, meta-tests, `CLAUDE.md`, and `symnav-stages.md` updated together with the package introduction. Telemetry added to the table.102103### Excluded104105- Any change to navigation command output, exit codes, or `daemon start|status|stop` output.106- Renaming `@symnav/renderer`. Revisit when a second output family exists.107- A persistence port in core or an on-disk index for cold runs.108- New CLI flags or environment variables.109- A second language backend.110- Any restructuring that changes an e2e parity or daemon suite expectation.111- Behavior changes surfaced by the reviews. Specified in `daemon-follow-ups-functional-spec.md`; they land after this restructuring.112113## Interaction Model114115### What a host provides to the daemon package116117- An executor: given argv, working directory, and telemetry flag, produces an ordered stream of stdout/stderr byte records and an exit code; can also release transient caches on request.118- The location of a module that constructs that executor, so the daemon's worker can load it in another thread or process.119- A state directory path.120- The product version, for compatibility checks.121- Per invocation: a workspace root and argv, or a control action (`start`, `status`, `stop`).122123### What a host receives124125- `execute(workspaceRoot, argv)`: a result identical in bytes to local execution, produced warm, cold, or by fallback. The host does not learn which route was taken except through the execution mode recorded for telemetry.126- `control(action)`: a lifecycle report the host renders.127128### What a host must not do129130- Read or write registry, socket, spool, or log files directly.131- Decide warm vs cold.132- Import from the daemon package's internal modules; only its public surface.133134### Locked threshold with value and reason. A threshold absent from the record is a defect.174175## Cross-cutting Concerns176177### Verification baseline178179The passing e2e parity and daemon suites on main are the baseline. The full-suite teardown flake and the unhandled daemon rejection are fixed before restructuring starts, so that baseline is green. Restructuring matches it exactly; a restructuring change that needs a test expectation changed is mis-scoped.180181### Documentation182183`CLAUDE.md` repo layout and dependency table, `plans/000/symnav-stages.md` package list update together with the introduction of `@symnav/daemon`.184185## Daemon Package Extraction186187**Purpose.** Give daemon policy and mechanism one home with an enforced boundary.188189**Produces.** `@symnav/daemon` with a public surface of: client (execute, control), process entry, worker entry, executor contract, policy object, lifecycle report shapes.190191**Does not produce.** Any navigation logic, any dependence on core, any knowledge of Commander syntax.192193**Example.** A contributor adds a new admission check. They add one guard in the daemon package and one rejection code. Nothing in `apps/cli` changes.194195**Edge cases.** Tests and benchmarks that imported daemon modules by deep relative path switch to the package's public surface or move into the package.196197## Executor Contract and Module Injection198199**Purpose.** Let the daemon run commands without knowing what they are.200201**Produces.** The daemon defines the executor's shape. The CLI implements it by re-parsing argv through the normal command program with retained backends. The CLI passes the location of its executor module; the daemon forwards it to the spawned process and worker thread, which load it and verify the expected export exists.202203**Does not produce.** A typed navigation request. A second execution path that bypasses the command program.204205**Edge cases.** Module missing or export absent: the worker reports a startup failure with a closed failure code; the daemon publishes failed startup; ordinary commands keep executing locally.206207## Client Routing Boundary208209**Purpose.** Keep CLI syntax in the CLI and daemon routing in the daemon.210211**Produces.** CLI classifies argv into local, control, or workspace; extracts `--cwd`; resolves the workspace root via core. Daemon client receives the root and argv and decides warm, cold, cold-plus-trigger, or fallback.212213**Does not produce.** A daemon that parses argv for anything but forwarding. A CLI that reads registry records.214215**Defaults.** Unchanged from `daemon-functional-spec.md` routing table.216217## Workspace Session in Core218219**Purpose.** Make retention a core object rather than CLI wiring.220221**Produces.** A session owning the workspace catalog and backends; prepares a scope (workspace, snapshot, router, refresh summary) for a start directory, with optional file selection. Cold runs create one per process; the daemon's worker keeps one alive.222223**Does not produce.** Any persistence beyond the process lifetime.224225## Revisioned Backend Base226227**Purpose.** Move language-agnostic retention out of the TypeScript backend.228229**Produces.** A core base that diffs file revisions, asks the subclass to prepare only added or changed files, publishes the index transactionally, tracks declarations by identity, and scopes a query cache to one turn. A core project-graph base that discovers configuration units, invalidates on input change, maps files to projects, and holds an inferred fallback project. The TypeScript backend extends both.230231**Does not produce.** Changes to what any command returns. A second backend.232233**Edge cases.** A backend that cannot prepare partially implements prepare as full rebuild; the base does not require partial support.234235## State Directory and Clock Ownership236237**Purpose.** Stop telemetry acting as a shared utilities package.238239**Produces.** CLI resolves `SYMNAV_STATE_DIR` or `~/.symnav` once and passes the path to telemetry and daemon. Daemon owns its wall and monotonic clock. Telemetry keeps only its own path helpers.240241## Lifecycle Rendering242243**Purpose.** Keep all formatting in the renderer package.244245**Produces.** Text and JSON rendering of start, status, and stop reports in `@symnav/renderer`, byte-identical to current output.246247## Guard-List Admission and Routing248249**Purpose.** Make the check order readable and each check testable alone.250251**Produces.** Admission: an ordered list (authenticated, worker ready, memory not paused, not draining, not a conflicting duplicate) where the first failing guard stops with a rejection code. Routing: an ordered list (record present, not starting, version compatible, responsive) producing warm, cold with reason, or fallback with reason. One closed rejection vocabulary owns "safe to retry locally".252253**Does not produce.** Chains for startup election, result delivery, or wire framing; those stay state machines.254255## Summary256257| Item                          | One line                                                                  |258| ----------------------------- | ------------------------------------------------------------------------- |259| `@symnav/daemon`              | Zero-dependency package owning every daemon concern                      |260| Executor contract             | Daemon-defined; CLI implements; injected as a module location            |261| Routing boundary              | CLI classifies argv; daemon client routes                                |262| `WorkspaceSession`            | Core owns retention as an object; no persistence port                    |263| Revisioned backend base       | Core owns revision diff, index, project graph, turn cache                 |264| State dir and clock           | CLI resolves path; daemon owns its clock; telemetry is a leaf            |265| Lifecycle rendering           | Moves to renderer; renderer may depend on daemon                          |266| Guard lists                   | Admission and routing as ordered guards with one rejection vocabulary    |267| Policy record                 | All thresholds in one object, reasons in `plans/005/daemon-policy.md`    |268| Behavior                      | Unchanged; defects found while restructuring are tracked separately      |
