A1 ↘

Move the lifetime owner; keep six habitats.

A core scope supplies six isolated handles held by the TypeScript service. Algorithms and key spaces stay in TypeScript; no package dependency direction changes.

Stated: core owns lifetime; independent key/value spaces need separate handles. The exact exported API, composition shape and files-only argument have no specific reason in the inspected prose.

A2 ↘

A cached entry is not every returned object.

Exact factory values survive repeated lookups, including undefined and rejected promises. A synchronous throw stores nothing. Reference and position results are projected again on access.

Stated: preserve query behavior and use Map.has because undefined is valid. No historical rationale for the projection choices was supplied.

A3 ↘

A failed refresh does not start a turn.

Only a successful refresh clears the current entries. The same handles serve the next turn. This ordering already exists in base and is newly pinned by a test.

Stated: failed refresh must preserve the last successful turn.

A4 ↘

Clearing and finishing are different boundaries.

Both versions clear entries before project cleanup. Head also awaits cleanup through the backend: a held cleanup keeps the call pending, and rejection reaches its caller.

Stated: old semantics must be unavailable during cleanup. Unexplained: why the new caller-visible wait/rejection fits the spec’s behavior-preservation rule.

A5 ↘

The cut does not cancel an escaped promise.

An old promise held by a caller can settle after a new turn. It does not replace the new entry. Clearing also leaves the handles usable.

Stated preservation intent covers promise settlement; the new core test pins settlement across turns.

B1 ↘

Policy owns the allowance; CLI owns its use.

Transport takes required transport/output/delivery slices. Delivery limits default to one fetch allowance per attempt and one outer reattachment. Test adapters replace legacy numeric knobs.

Stated: omitted composition must not recreate defaults; test tuning must not restore production compatibility overloads.

B2 ↘

Reset the inner allowance, retain the outer budget.

Each executeOnce creates fresh output, receiver and fetch counter. The outer reattachment counter persists across attempts; the same request identity is sent again. Default recovery is preserved.

Stated: each reattached attempt needs its own fetch allowance; reattachment recovers the accepted request without local replay. Base already has per-attempt fetch state; head makes both limits numeric policy inputs.

B3 ↘

A number grants permission, not a retry loop.

Fetch needs acceptance, a manifest, an unsettled nonterminal attempt and remaining allowance. Reattachment needs an authenticated accepted close. An incomplete fetched stream stops after one fetch even with allowance three.

Stated: preserve distinct attempt limits. No reason for larger fetch budgets lacking a repeated-fetch path was found; the default remains one.

B4 ↘

The later failure can become the visible specimen.

If a reattached completion rejects, base returns the first close error; head can return the later error. If starting the reattachment itself rejects, both retain the first error.

Unexplained: no error-selection rationale was found in the PR body, commits or inspected spec. This is a caller-visible change beside the counter refactor.

E1 ↘

Preservation has a bounded evidence trail.

The five original #127 service tests and helpers are unchanged; six service and four core tests are added. #131 adds a reattached-fetch case. Our focused head suites pass 15 and 35 cases.

Stated: characterization and policy-preservation intent. Unexplained: exact test selection; no end-to-end parity or full-PR test audit is claimed.
