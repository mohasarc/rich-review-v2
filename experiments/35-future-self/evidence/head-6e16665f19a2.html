1# Symnav Daemon Functional Spec
2
3## Goal
4
5Symnav keeps a reusable workspace daemon so repeated navigation commands avoid rebuilding the same project state. Ordinary commands never wait for daemon startup: they answer locally while one daemon warms in the background, then later commands switch to the ready daemon. This must remain useful on representative workspaces and on projects up to ten times larger. The daemon is not a language server, a network service, or a new navigation surface. This spec defines product behavior only and avoids implementation choices.
6
7## Primary User
8
9The first-class user is a coding agent issuing many symnav commands during a long development session.
10
11Its default experience is:
12
13- First command starts one background warm-up and answers locally.
14- Further commands answer locally while warm-up continues.
15- Commands use the daemon after it becomes ready.
16- No navigation output reveals which route answered it.
17
18Explicit alternatives are `symnav daemon start|status|stop` for lifecycle control and `SYMNAV_DAEMON=0` for fully local execution.
19
20## Core Guarantees
21
22### Ordinary commands never wait for warm-up
23
24An ordinary command starts local execution without waiting for a daemon to become ready.
25
26```text
27If no ready daemon exists when a command is accepted, that command answers locally while one daemon warms independently.
28```
29
30The route chosen when a command is accepted does not change midway through that command. A daemon becoming ready does not cancel or duplicate local work already in progress.
31
32Examples:
33
34- First `resolve` in a large workspace starts warm-up and runs locally at once.
35- A second `overview` issued ten minutes into a twenty-minute warm-up also runs locally at once.
36- First command after readiness uses the daemon.
37- A warm-up failure does not delay or alter local command output.
38
39There is no flag that makes ordinary navigation commands wait for warm-up.
40
41### One durable warm-up per workspace
42
43Concurrent callers share one warm-up. Initiating caller does not own daemon lifetime.
44
45```text
46For one workspace and state location, at most one daemon is starting or ready, regardless of caller count or caller lifetime.
47```
48
49The daemon continues warming after initiating command exits. Later callers observe or adopt that warm-up; they do not restart it. A caller failure, timeout, or disconnect cannot stop a healthy warm-up.
50
51Examples:
52
53- Ten commands begin together in a cold workspace. All ten answer locally and exactly one daemon warms.
54- Initiating process exits one second after launch. Warm-up continues to readiness.
55- A healthy warm-up takes twenty minutes. It is not discarded because of project size or elapsed time.
56- Warm-up process exits. Starting state is cleared promptly and a later eligible command may try again.
57
58There is no healthy-startup timeout override because healthy automatic warm-up has no project-size deadline.
59
60### Warm answers equal local answers
61
62A command answered by the daemon produces the same stdout, stderr, and exit code as the same command run locally against the same workspace state.
63
64```text
65For any command, arguments, cwd, and workspace contents:
66output(daemon) == output(local), byte for byte, including exit code.
67```
68
69Warnings, errors, `--help`, `--version`, and `--json` are covered. There is no daemon-only navigation output and no local-only navigation output.
70
71There is no parity override.
72
73### Answers reflect current workspace state
74
75Every request sees workspace contents current when its execution turn begins.
76
77```text
78A request never answers from workspace state older than start of its execution turn.
79```
80
81For local commands, execution turn begins when local execution starts. For queued daemon commands, it begins when command reaches front of queue.
82
83Examples:
84
85- A file edited after one request is reflected in next request.
86- A queued request sees edits completed before its queue turn begins.
87- Added, deleted, and renamed files appear in next answer.
88
89There is no stale-data override.
90
91### Nested Git workspaces are separate boundaries
92
93Selected workspace is nearest Git workspace containing caller. A descendant directory with its own Git workspace marker belongs to a separate workspace.
94
95```text
96Parent commands never traverse, index, refresh, or return files from a nested repository, worktree, or submodule.
97```
98
99This boundary is independent of ignore rules. Ignore negation cannot pull a nested workspace back into its parent.
100
101Examples:
102
103- A parent repository containing `.worktrees/feature` does not return symbols from that worktree.
104- Running with `--cwd .worktrees/feature` selects and navigates worktree normally.
105- Directly targeting a nested-workspace file from its parent fails with guidance to select nested workspace.
106- A directory named `.worktrees` with no nested Git workspace remains ordinary workspace content.
107
108There is no include-nested-workspaces override.
109
110### Slow or busy does not mean dead
111
112Long startup, queue wait, and command execution are not daemon failures.
113
114```text
115Only authenticated evidence of process exit, protocol incompatibility, or corrupt communication invalidates daemon ownership.
116```
117
118A caller timeout or disconnect does not remove a live daemon record, stop a healthy daemon, or replay accepted work locally. A short command queued behind long work cannot destroy daemon state.
119
120Lifecycle status remains responsive while navigation work is running and reports daemon as busy rather than absent.
121
122There is no force-invalidate-on-timeout override.
123
124### Resource failures are controlled
125
126Supported workloads do not end with raw out-of-memory output, partial responses, or an unreported daemon disappearance.
127
128```text
129A resource or response-size limit produces either a complete normal answer or a complete symnav error while preserving recoverable daemon state.
130```
131
132Known capacity failures are not immediately repeated through equivalent local execution. A large response does not by itself mark daemon corrupt.
133
134There is no raw-failure override.
135
136## Scope
137
138### Included
139
140- Background warm-up for `overview`, `resolve`, `def`, `refs`, `context`, `graph`, and `stats`.
141- Local answers during warm-up.
142- One durable starting or ready daemon per workspace and state location.
143- Startup that may take at least twenty minutes without a healthy-startup deadline.
144- Warm execution with byte-for-byte local parity.
145- Current-state refresh before each command's execution turn.
146- Nested repository, worktree, and submodule boundaries.
147- FIFO navigation execution within one ready workspace daemon.
148- Responsive lifecycle control during navigation work.
149- Controlled handling of long commands, caller disconnects, resource pressure, and large responses.
150- Explicit `daemon start`, `daemon status`, and `daemon stop`.
151- `SYMNAV_DAEMON=0` local-only execution.
152- State-location isolation through `SYMNAV_STATE_DIR`.
153- Version mismatch replacement.
154- Diagnostic logs and execution-mode telemetry.
155- Gating performance and resource measurements on realistic and scaled workspaces.
156
157### Excluded
158
159- Concurrent navigation execution within one workspace daemon.
160- Cross-workspace shared project state.
161- Traversing nested Git workspaces from a parent command.
162- A network-reachable daemon or third-party protocol.
163- Persisting a loaded workspace across daemon restarts.
164- A user flag for startup timeout, request timeout, idle timeout, or memory limit.
165- New navigation commands or changes to navigation result grammar.
166- File-watcher configuration exposed to users.
167- Support for non-TypeScript language backends beyond existing participation contract.
168
169## Interaction Model
170
171### Ordinary commands
172
173Existing invocations are unchanged:
174
175```console
176$ symnav resolve PaymentProcessor
177$ symnav overview src/checkout/CheckoutService.ts
178$ symnav refs CheckoutService::processPayment
179```
180
181`--cwd <dir>` selects both workspace and daemon. A command never accepts a daemon name, process identifier, endpoint, or nested-workspace inclusion flag.
182
183### Daemon commands
184
185```console
186$ symnav daemon start
187$ symnav daemon status
188$ symnav daemon stop
189```
190
191`start` and `stop` act on workspace selected by current directory or `--cwd`. `status` lists validated daemon state for current user and configured state location. All three accept `--json`.
192
193### Local-only execution
194
195```console
196$ SYMNAV_DAEMON=0 symnav refs CheckoutService::processPayment
197```
198
199No daemon is contacted or started. Output remains equivalent to warm execution.
200
201### State-location isolation
202
203```console
204$ SYMNAV_STATE_DIR=/tmp/session-a symnav resolve PaymentProcessor
205```
206
207Registry, logs, endpoints, and daemon ownership are isolated from clients using another state location. Separate state locations do not collide or invalidate each other's daemons.
208
209## Output Format
210
211Navigation output is unchanged.
212
213### `daemon start`
214
215Ready:
216
217```console
218$ symnav daemon start
219Daemon ready for /Users/mo/projects/reelcut
2202142 files loaded in 9.8s
221```
222
223Already running:
224
225```console
226$ symnav daemon start
227Daemon already running for /Users/mo/projects/reelcut (pid 48213, up 14m)
228```
229
230An explicit start waits until readiness or a confirmed startup failure. A healthy twenty-minute startup remains attached and produces no progress bytes before its final response.
231
232### `daemon status`
233
234Ready daemons:
235
236```console
237$ symnav daemon status
238/Users/mo/projects/reelcut pid 48213 ready up 14m 2142 files 1.3 GB last request 8s ago
239```
240
241Starting or busy daemons:
242
243```console
244$ symnav daemon status
245/Users/mo/projects/large-workspace pid 48301 starting 12m memory 2.1 GB
246/Users/mo/projects/reelcut pid 48213 busy refs 43s queued 2 memory 1.6 GB
247```
248
249No daemons:
250
251```console
252$ symnav daemon status
253No daemons running.
254```
255
256Status never reports a live busy daemon as absent merely because its current command is slow.
257
258### `daemon stop`
259
260```console
261$ symnav daemon stop
262Stopped daemon for /Users/mo/projects/reelcut (pid 48213)
263```
264
265When absent:
266
267```console
268$ symnav daemon stop
269No daemon running for /Users/mo/projects/reelcut
270```
271
272Both cases exit `0`.
273
274### Controlled capacity failure
275
276```text
277Cannot answer: workspace operation exceeded available resources.
278```
279
280Error is complete, uses normal symnav error output, and does not include a runtime crash dump.

282## Cross-cutting Concerns
283
284### Routing and queueing
285
286Routing is decided once per command:
287
288| State when command is accepted | Behavior |
289| ------------------------------ | ------------------------------------------------------------- |
290| No daemon | Trigger one background warm-up and execute locally |
291| Starting | Execute locally without waiting or starting another daemon |
292| Ready and idle | Execute through daemon |
293| Ready and busy | Queue through daemon in arrival order |
294| Confirmed dead or incompatible | Clear invalid ownership, trigger replacement, execute locally |
295
296Lifecycle requests remain independent of navigation queue responsiveness.
297
298### Lifetime
299
300- Idle exit: `30 minutes` after last completed navigation request.
301- Warm-up time does not count as idle time.
302- Navigation activity resets idle period.
303- Workspace deletion, explicit stop, confirmed incompatibility, or controlled resource shutdown may end daemon sooner.
304- Initiating and waiting caller lifetimes do not control daemon lifetime.
305
306### Performance targets
307
308Targets are measured end to end on a representative worktree of about 4,000 TypeScript files after daemon readiness:
309
310```text
311Targeted overview: under 500 ms
312Resolve and def: under 2 s
313Refs, context, and graph: under 5 s for representative depth-one queries
314```
315
316Warm no-change performance is measured repeatedly, not from one best run. Targets include freshness, command work, rendering, and transport, but exclude queue wait.
317
318Scale gates cover realistic workspaces at `1x`, `2x`, `3x`, and `10x` reference-workspace size. Every gate records startup duration, command duration, queue wait, peak memory, response size, result parity, freshness after changes, and daemon continuity.
319
320A scale gate may take longer as project size grows. Representative commands at every scale complete under default resource policy. A gate does not pass if daemon restarts, disappears from status, emits raw resource failures, or retries accepted work locally.
321
322### Diagnostics
323
324Daemon diagnostics record:
325
326- Startup duration and outcome.
327- Queue depth and queue-wait duration.
328- Current command and elapsed time.
329- Workspace discovery and freshness duration.
330- Navigation and rendering duration.
331- Response size.
332- Current and peak memory.
333- Controlled shutdown and confirmed crash reason.
334
335Diagnostics never appear in navigation stdout or stderr.
336
337### Telemetry
338
339Execution mode remains `warm`, `cold`, or `fallback`.
340
341- Local commands during healthy warm-up are `cold`.
342- Commands replayed locally after a pre-acceptance daemon failure are `fallback`.
343- A command accepted by daemon is recorded once and is not also recorded as fallback because caller disconnected.
344- `SYMNAV_TELEMETRY=0` disables telemetry in every mode.
345
346### Platforms
347
348Behavior applies on macOS, Linux, and Windows. Warm and local parity runs on supported CI platforms.
349
350## Transparent Background Warm-up
351
352**Purpose.** Build reusable project state without making ordinary commands wait.
353
354**Produces.** One local answer per command until daemon is ready, then warm answers.
355
356**Does not produce.** Startup banners, progress output, duplicate daemons, duplicate command answers, or partial output.
357
358Example:
359
360```console
361$ symnav resolve PaymentProcessor # local answer; warm-up starts
362$ symnav overview src/orders.ts # local answer; same warm-up continues
363$ symnav def PaymentProcessor::charge # warm answer after daemon becomes ready
364```
365
366**Defaults.** Enabled.
367
368**Edge cases.** Concurrent first calls elect one warm-up. Caller exit does not cancel it. Confirmed startup failure clears starting state so a future call may retry.
369
370## Explicit Daemon Start
371
372**Purpose.** Wait for a workspace to become warm before beginning a navigation session.
373
374**Produces.** One readiness or already-running response.
375
376**Does not produce.** Navigation output or a healthy-startup timeout.
377
378**Edge cases.** Concurrent explicit starts wait for same daemon. A child failure returns promptly. `SYMNAV_DAEMON=0` prints `Daemon disabled by SYMNAV_DAEMON=0` and exits `1`.
379
380## Daemon Status
381
382**Purpose.** Show starting, ready, busy, and queued work without disturbing it.
383
384**Produces.** Workspace, state, process identifier, uptime or startup elapsed time, file count when known, memory, current command when busy, queue depth, and last-request age.
385
386**Does not produce.** False absence because a command blocks navigation work, records from another state location, or data about another user.
387
388**Defaults.** Workspace-path sort order. Status response target: `1 second`.
389
390**Edge cases.** Confirmed stale records are removed. An unresponsive but live process is reported as unresponsive, not silently omitted. Status never invalidates a daemon.
391
392## Daemon Stop
393
394**Purpose.** End background work and release memory explicitly.
395
396**Produces.** Stopped, killed, or absent confirmation.
397
398**Does not produce.** An error for an absent daemon.
399
400**Defaults.** Graceful wait: `5 seconds`, then controlled termination.
401
402**Edge cases.** An in-flight request may complete during graceful wait. Forced stop produces one complete outcome for its connected caller and removes daemon ownership after process exit.
403
404## Warm Navigation
405
406**Purpose.** Reuse loaded workspace state for repeated commands.
407
408**Produces.** Current, byte-equivalent navigation answers within scale targets.
409
410**Does not produce.** Results from nested workspaces, stale results, raw resource failures, or full repeated local work after caller timeout.
411
412**Edge cases.** Long results transfer completely or fail with a controlled result-size error without invalidating daemon. Package aliases and workspace imports resolve with same correctness as local project execution. Empty reference, context, or graph results mean there are no results, not that workspace imports were skipped.
413
414## Summary
415
416- Ordinary commands answer locally while one daemon warms independently.
417- Healthy warm-up may take twenty minutes or more without being discarded.
418- Exactly one daemon starts per workspace and state location.
419- Ready commands are current and byte-equivalent to local execution.
420- Nested Git workspaces never leak into parent results.
421- Slow, queued, and disconnected callers do not invalidate healthy daemon state.
422- Status stays truthful and responsive during long work.
423- Resource and response-size failures are controlled and never blindly replayed.
424- Realistic 1x, 2x, 3x, and 10x reference-workspace gates cover latency, memory, parity, freshness, and continuity.
