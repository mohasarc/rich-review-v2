## 2. The change in at most three sentences

PR 148 gives the `@symnav/daemon` package its own copies of the daemon mechanisms (43 new production files next to 8 existing ones: transport, process coordination, registry, worker, lifecycle, delivery, client routing, clocks, result capture) plus a public `DaemonClient` doorway and real process/worker entry subpaths. The shipped CLI is not switched over: it keeps running its own 38 mechanism copies, now frozen (apparently hash-pinned), composed by a CLI-owned dispatcher and two CLI-owned invocation modules. Along the way, clock ownership moves from telemetry into the daemon, a temporary policy-testing export and its lint checks are removed, and 37 mechanism test files move into the package with some assertions changed or deleted.

## 3. Boxes and boundaries

- **Box A — `apps/cli` `src/daemon` ("CLI / old home", amber):** 41 files = 38 frozen mechanism copies ("Dim = frozen compatibility role — still active") + 3 CLI-owned invocation files: the CLI dispatcher and two invocation modules (map labels in the visible text: "Invocation route", "Argv selector"). The dispatcher constructs CLI-local collaborators (default side panel: "There is no dispatcher → DaemonClient edge in this snapshot").
- **Box B — `@symnav/daemon` `src` ("Package / new home", teal):** 43 added + 8 existing ("Existing package surface", grey) = 51 files, grouped in directory rings: registry/, execution/, delivery/, resources/, transport/, process/, lifecycle/, client/, diagnostics/, worker/, plus root-level items (process entry, worker entry, and the grey existing surface). Public face: package root export + `process-entry` and `worker-entry` subpaths (entries export no named API). `DaemonClient` (client/) is the public doorway; its Node runtime is loaded dynamically at construction.
- **Box C — the host (outside both circles, implied):** supplies command syntax, the executor implementation/URL, and readiness syntax. The package does not own these.
- **Box D — telemetry (implied, not drawn):** used to own the daemon's clock; no longer does.
- **Tests (outside the map per footer):** 37 mechanism test files move from CLI side into the package; CLI entry test removed; new public/entry boundary tests.

Boundaries that moved:
1. **Mechanism ownership CLI → package** (copy, not move: the CLI keeps its copies frozen). The *invocation* boundary did **not** move: the production consumer is still the CLI's own graph.
2. **Launch path** (launcher → process → worker) gains a package home with real entry subpaths; the host–package line runs between "launch machinery" (package) and "command syntax + executor implementation" (host).
3. **Route and result ownership** sits in the package client: routing guards, local replay decision, result capture/cleanup.
4. **Clock ownership telemetry → daemon** (injectable wall + monotonic clocks).
5. **Dependency boundary:** the package has no production import of another symnav package.
6. **Test boundary:** private-mechanism tests live inside the package; public/entry boundaries are enforced by new tests.

Numbers seen: 43 added, 8 existing, 38 frozen copies (38/38 remain), 3 invocation files, 92 files, 59 "selected" dependencies, 37 moved test files, 7 readings.

## 5. Questions the top layer left open

1. Where is the "production consumer switch" — a later PR? Does anything in production change behavior in PR 148, or is it purely additive for the shipped CLI?
2. How is the freeze enforced: a test comparing CRLF-normalized hashes (the default panel shows a receipt labelled "compatibility copy.test")? What fails, and what is someone supposed to do, when a CLI copy must change?
3. Are the package files verbatim copies of the 38 CLI files, or already-diverged rewrites (e.g. the telemetry → daemon clock move of reading 06: does the CLI copy still use telemetry's clock)? Which 5 of the 43 added files have no CLI counterpart?
4. What exactly are the two invocation modules, and why do they stay CLI-side?
5. What does "disabled" mean (config? env?) and why does disabled status/stop stay available?
6. "Separate status timeouts" — separate from what, and what values?
7. What is the readiness command, what does "cold" mean, and who calls it?
8. What was the "temporary policy-testing export" used for, and what did the deleted lint checks enforce? Does removing them loosen any guarantee?
9. Route guards: what does each guard check, and what happens when each fails (local run? spawn? error)? What makes warm-up "eligible"?
10. Which transport failures count as retry-safe; what happens on a non-retry-safe failure (error surfaced to user?)?
11. What are "narrow coordinates" and "full mutation snapshots"; what is "startup ownership"?
12. Why do the three authentication paths differ, and is that a security-relevant inconsistency or deliberate?
13. Windows: does "without a termination diagnostic" lose a diagnostic in production, or only change a test expectation?
14. Deleted readiness startup/duration assertions: is that coverage lost for good, and is it connected to the clock move or the deferred idle-window change?
15. Why serialize Vitest files (shared resources? flakiness?) and why tsx?
16. "59 selected dependencies" — selected by what criterion; which edges are omitted?
