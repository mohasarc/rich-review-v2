## 2. The change in at most three sentences

PR 148 adds a new, package-owned (private) daemon routing policy that decides, per invocation, whether to route to a warm daemon or run locally, using four ordered guards: a registry record exists → the record is not "starting" → the record's version matches → the daemon responds to a probe, with the first guard that returns ending the decision. The policy reads the registry once and probes at most once (lazy, promise reused), maps each failure/absence case to a route kind + reason (cold/absent, cold/recovering, cold/starting, fallback/incompatible, fallback/dead, warm), and a client dispatches warm → daemon, everything else → local, additionally firing a non-blocking warm-up for absent/fallback outcomes. The shipped CLI keeps its own byte-identical dispatcher for now, so the consumer switch is a separate, later review; the page claims behavior is preserved (17 controlled base/head pairs agree) and the PR adds 15 policy + 29 client tests.

## 3. Boxes and boundaries

- **Package runtime (new owner)**: contains a *private* routing policy (the four guards + route/reason mapping) and, by inference from "29 client tests" and reading C, a client that turns a route into dispatch (warm → daemon, else → local; warm-up request for absent/fallback; disabled bypass).
- **Shipped CLI (unchanged)**: still contains its own byte-identical dispatcher and tests; still the active path ("CLI still active" on the stage). So after this PR there are two homes for the routing logic.
- **Registry** (external port): record read once; carries a state (starting / ready / …) and a symnav version. "Read throws" is a distinct case.
- **Observer / probe** (external port): observes the record's daemon at most once; outcomes: responsive pong (with its own version and state starting/ready/busy), starting, throws, unresponsive, exited, incompatible, corrupt.
- **Removal** (external effect): process-matched removal of a record, attempted only on "exited"; errors ignored.
- **Warm-up** (external effect): independent request, not awaited, does not change the route.
- **Boundary that moved**: ownership of routing selection moves from the CLI into a new package runtime (as a private policy). The consumer boundary did *not* move in this PR: the CLI does not yet call the package. Ownership move and consumer switch are deliberately split into separate reviews.

## 5. Questions the top layer left open

1. Who consumes the new package policy in this PR if the CLI still uses its own dispatcher? Is the package policy/client exercised only by its tests until a later PR?
2. Is the package policy a copy of the CLI logic? What prevents the two homes from drifting before the switch?
3. What does "private" mean concretely — not exported from the package, internal module, or class-private?
4. Lifetime of the "one lazy context": per routing call? Could the reused observation promise be shared across calls?
5. What distinguishes cold/starting from cold/recovering in consequences (both skip warm-up; do they differ in anything the client does)?
6. Why does a matching pong in "starting" become cold/recovering while an observer "starting" becomes cold/starting? (Page marks this as unexplained.)
7. What exactly is "process-matched" removal (PID match against the record?) and what else counts as "dead"?
8. How is warm-up requested and what happens to its errors? Is there any de-duplication?
9. Where does "disabled" come from (env/config/flag), and why does the policy's route union keep it?
10. Probe timeouts / "unresponsive" threshold — no timing information at all.
11. "not full-PR parity or an audit of unrelated test changes": what else is in PR 148 beyond routing selection, and which unrelated tests changed?
12. Who ran the 17 controlled base/head pairs (the page author, not the PR)? What does "base" mean for a package policy that did not exist at base (presumably the CLI dispatcher at base)?
