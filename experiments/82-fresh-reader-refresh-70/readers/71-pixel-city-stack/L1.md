## 2. The change, in my words (≤ 3 sentences)

Across 26 dependent PRs (#123–#149; #125 is absent from the scrubber), daemon functionality moves out of the CLI app into a new `@symnav/daemon` package. First, reusable workspace machinery moves to core and a contracts-only daemon leaf package is created. Next, the CLI's daemon mechanisms are split into smaller owners in place. Then #148 stages the full package (DaemonClient façade plus mechanisms, with 38 CLI copies frozen and 37 test files relocated), and #149 switches CLI invocation to DaemonClient, deletes the frozen copies, and fences ownership with a read-only test inspector and compiler-based checks.

## 3. Boxes and boundaries

Units (districts = package/app), with standing-path counts from the default #148 skyline labels:
- **CLI** (`apps/cli`, "CLI host", 99 standing paths): argv/workspace coordination, hosting, format selection and writing. Before #149 it also holds the active daemon graph ("CLI entry → CLI dispatcher → local transport").
- **DAEMON** (`@symnav/daemon`, 129): starts as a leaf holding policy, command/failure vocabulary and admission authority (#129–134). Gains DaemonClient and the mechanisms in #148, then entry points and transport composition in #149.
- **CORE** (11): gains source caching, revision publication, project membership, semantic-cache lifetime and workspace sessions (#123–128).
- **TYPESCRIPT** (13): keeps language-specific work.
- **RENDERER** (5): gains lifecycle report formatting (#135–136).
- **TELEMETRY** (3): loses state-directory resolution to CLI (#129–134).
- **META-TESTS** (5) and **REPOSITORY** (8, infrastructure annex): no ownership change stated. Reading 06 mentions "compiler-based ownership checks" but does not say where they live.

Boundaries that moved, in order:
1. TypeScript/CLI → core: the reusable mechanisms (#123–128).
2. telemetry → CLI: state-dir resolution. A new daemon box appears holding contracts only, with no internal production dependencies, and CLI mechanisms depend on it (#129–134).
3. The daemon ↔ CLI execution boundary inverts: CLI plugs in through an injected executor module behind a daemon-owned contract. Report formatting crosses CLI → renderer (#135–136).
4. Inside CLI, one daemon block is subdivided into separate owners: codec, transfer receiver, socket client/server, activity projector, worker generations, delivery, accepted execution (#137–147).
5. The mechanisms cross CLI → daemon as a staged copy while the CLI path stays active. DaemonClient's public façade loads the private runtime dynamically (#148).
6. The invocation boundary crosses: CLI → DaemonClient. CLI copies are deleted, the daemon owns entry points and transport composition, and tests observe through a read-only inspector (#149).

## 5. Questions the top layer left open

2. What does the injected executor module contract look like? How is the module located and loaded, and what happens if loading fails?
3. The façade "loads its private runtime dynamically". What happens on a load failure, and what exactly are the "host declarations" kept free of Node-backed mechanisms?
4. What does "frozen" mean for the 38 compatibility files: enforced (a test, a lint) or convention only? Are they byte copies of the package files?
5. Which blue test buildings stay in CLI after #149, and why? Is it the same set as, or overlapping with, the 37 moved tests?
6. What did tests have before the read-only inspector ("storage authority")? What can they no longer do?
7. What are the "compiler-based ownership checks", where do they live (meta-tests?), and what do they forbid?
8. Which startup/result timing checks were dropped? Is that behavior covered anywhere else?
9. Does any user-visible CLI behavior change (commands, output, errors), or is the whole stack structure-only?
10. What are "worker generations", and what is "accepted execution"?
11. Why is #125 missing from the 26-PR sequence?
12. Is renderer a new package in #135–136 or an existing one?
13. Does telemetry now receive the state directory from CLI? What changed for telemetry callers?
