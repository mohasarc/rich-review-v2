## 2. The change in at most three sentences

PR 131 changes where CLI daemon mechanisms get their limits and timeouts. Output capture/spool/worker caps, startup and shutdown clocks, resource thresholds, diagnostics limits, transport timeouts and delivery retry budgets now come from required slices of the existing DaemonPolicy snapshot, not CLI-local defaults and numeric overrides. The CLI's own resource-policy derivation and the production compatibility overloads are deleted, but the mechanisms themselves stay in apps/cli and DaemonPolicy itself is unchanged. Tests move behind seven test-only adapters. Five unexplained side changes ride along: a different reported error after reattachment, fixture translation, deleted derivation assertions, tests that cast through unknown, and an earlier parent-side policy parse.

## 3. Boxes and boundaries

- **packages/daemon: DaemonPolicy.** The owner of threshold values: a policy snapshot with named sections (output, startup, shutdown, resources, diagnostics, transport, delivery). It is "unchanged in #131": no edits to the policy itself in this PR.
- **apps/cli: mechanisms.** 17 distinct production files read policy directly. Mechanisms named in the survey:
  - capture, spooling, disk decoding, both worker endpoints (worker host + worker), raw-number validators
  - registry grace, heartbeat, authorization, observation, previous-instance termination, child retry
  - idle lifetime, user stop, signal waits, drain acknowledgement, forced-stop reserve
  - RSS thresholds, hard cap, worker heap, sampling cadence, "replacement circuit"
  - log rotation, backups, write queue, disconnected traces
  - transport timeouts (status-observer 100 ms, ordinary 250 ms, admission 5 s) and frame caps
  - execution reattachment and result-fetch budgets
- **Test side (apps/cli tests + meta-test):**
  - seven new test-only helper adapters that turn legacy test knobs into validated policy
  - a meta-test that rejects retired names
  - benchmark resource reports
- **Boundary that moved: authority over numbers.** Before, the CLI held "local defaults + numeric overrides" (the survey names a CLI resource-policy class, a memory-cap input, retired constants and an unused startup-timeout knob). After, every mechanism requires a policy slice as input. Threshold ownership crosses from apps/cli to the daemon package's snapshot; the mechanism code does not cross.
- **Test boundary moved.** Tests no longer reach production compatibility overloads. They go through a test-only adapter boundary; clock/storage/worker seams remain.
- **Failure boundaries shifted (flagged as faults):**
  - Snapshot validation now also happens in the parent before a Worker exists, so it fails earlier and synchronously (F5).
  - Which completion error escapes after a successful reattachment receipt changed (F1).

## 5. Questions the top layer left open

1. **Numeric values:** did any runtime number actually change? Are the DaemonPolicy defaults identical to the retired CLI constants? Only a few rows say "keeps"/"remains" (one retry, 5 s, min(...) reserve).
2. **"Numeric overrides":** user-facing options/env vars, or internal constructor parameters? Did anything a user could configure disappear, e.g. the "memory-cap input"?
3. **The snapshot's origin:** where is it created and validated, who composes the slices, and how is it serialized to the worker?
4. **Terms left undefined:**
   - What is the "replacement circuit" (Resources)?
   - What are "lost warm-up" and "election recovery" (Startup)?
   - What is the "status observer" (Transport)?
5. **F1:** what user-visible effect does the error-provenance change have (which message a user sees)? Is it a fix or a regression?
6. **F5:** can an invalid serialized snapshot really reach the worker host if the policy is validated earlier? How likely is the new synchronous parent-side throw?
7. **F3:**
   - Is the removed "250 ms constant assertion" the same 250 ms as Transport's ordinary timeout?
   - What exactly is lost without the 256 MiB row?
8. **F4:** do expectations that read policy defaults turn some tests into self-comparisons?
9. **Names not given:**
   - Which 17 files are the direct readers?
   - What are all 13 overlaps? The map draws only 6.
   - Which are the seven adapters, and which retired names does the meta-test ban?
10. **Stack and verification:**
    - Does DaemonPolicy come from an earlier PR in the stack? ("unchanged in #131" implies it already existed.)
    - Do the tests pass or was anything run? The top layer makes no claim either way.
