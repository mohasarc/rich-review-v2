## 2. The change in at most three sentences

PR 127 replaces the TypeScript query service's six hand-managed Maps and six manual clears with a generic lifetime class from core: the service owns one `TurnScopedCacheScope`, which creates six isolated `TurnScopedCache` handles (callers only get `getOrCreate`) and synchronously clears all of them on `beginTurn` and release. Lookup behavior is meant to be preserved exactly (same keys; undefined, empty and rejected values stay cached; a synchronous factory throw stores nothing; an old promise can settle but never overwrites a newer entry; clearing still happens only after a successful refresh and before project cleanup). Along the way head narrows the exported service's `beginTurn` argument from the whole snapshot to readonly files, turns service release from `void` into `Promise<void>` awaited through backend → service → project graph (so pending cleanup delays backend release and cleanup rejection reaches its caller, where base returned early), and adds 4 core + 6 service tests.

## 3. Boxes and boundaries

| Box | Inside it (head) | What moved / how |
|---|---|---|
| **core** (package) | New exported generic lifetime classes: `TurnScopedCache` (handle; `getOrCreate`) and `TurnScopedCacheScope` (`createCache`, `beginTurn`, `releaseTransientResources`); the scope retains registered handles and clears their Maps synchronously. | Gains ownership of "clear" / turn lifetime. Dependency TypeScript → core already existed; no new edge. |
| **TypeScript query service** | Still owns the service instance, the query algorithms and the key spaces; now owns one scope + six handles: definitions, reference locations, call targets, callers, callees, position definitions. Keys: symbol identity for five stores, path + offset for position definitions. Per-call return shapes kept (references project cached locations each call; position definitions rehydrate nodes into a new array; four others return stored promise). | Base: "six Maps + six manual clears". Head: "one scope + six handles / lifetime class supplied by core". Exported `beginTurn` now takes readonly files instead of the whole snapshot; release returns `Promise<void>`. |
| **backend** | Refresh boundary (clears only after awaited refresh succeeds; failed refresh keeps entries); release boundary; async wrappers over service queries ("a different observation surface"). | Release now awaits service release, which awaits project-graph cleanup; base returned early. |
| **project graph** / **concrete TypeScript project cleanup** | Graph "accepts async cleanup"; concrete TS project cleanup is synchronous. | Now sits at the end of an awaited chain; cache clear still happens before this cleanup. |
| **caller** | Holds references to promises returned from lookups. | Unchanged contract: clearing does not cancel its promise; that promise's settlement cannot replace the next turn's entry. |

Boundary that moved: per-turn cache lifetime (storage + clear) crosses from the TypeScript service into core; the query/algorithm boundary does not move. A second, smaller boundary shift: the release call's completion/rejection now crosses back up from project graph to backend caller.

## 5. Questions the top layer left open

1. What exactly was the spec's "proposed extension shape" (subclassing a core base? mixin?), and did choosing composition cost anything?
2. What precisely is a "turn"? Only a successful backend refresh starts one — is there any other trigger, and is `releaseTransientResources` also end-of-turn or only shutdown?
3. For T11: if no newer entry exists yet for that key in the new turn, can the old settlement populate the empty slot? The phrasing "cannot overwrite a newer entry" leaves that case implicit (the lede's "or let it replace the next entry" suggests no).
4. Rejected promises stay cached until the next turn: is there any memory/staleness bound, or can a failed query stay failed for a long turn?
5. Which six files changed? Does the project graph file change in this PR, or did it already await async cleanup?
6. Who calls backend release, and do they now await it / handle the newly propagated rejection? Any caller that ignored the old `void` return now gets a floating promise?
7. Does narrowing `beginTurn` to readonly files change any caller code or remove information the service needed from the snapshot?
8. Is `Map.has` presence-checking a preservation of base, or a fix to a base truthiness check? ("preserve existing … behavior; Map.has admits cached undefined" reads as preserved.)
9. Does the scope's retention of registered handles ever release them (e.g., if a service is discarded)?
10. Do the six new service tests also pass on base (true characterization) or only on head?
11. Headline "Same lifetime behavior." vs reading 06's changed release completion/rejection — which one should a reviewer trust as the summary? (The band itself says "A separate release await also changes when the backend call finishes".)
