## 2. The change in at most three sentences

Across a 26-PR stack (#123-#149, no #125), the daemon's per-request turn keeps its causal order. The order is accept once -> await worker -> seal bytes -> publish terminal -> wait for stream -> boundary resource sample -> next turn, with cleanup and ACK on a separate branch outside the FIFO. What changes is ownership: these steps move out of a single "process shell" into dedicated owners. Worker generations go to a generation manager (#145), stream delivery plus cleanup/ACK go to a delivery session (#146), and acceptance, sealing and boundary sampling go to an execution session (#147). #148 stages a daemon package while the active CLI path still uses the frozen graph, and #149 switches the CLI to the package, leaving only invocation (argv/workspace) host-owned. The headline invariant: a ledger "completed" does not open the FIFO, because the next request waits for the tracked stream delivery and the end-of-turn sample to settle.

## 5. Questions the top layer left open

1. What is "sealing bytes"? What "completion storage" is (spool? file?), and what happens if sealing fails?
2. What does "publish terminal" consist of: only a ledger state change, or also a notification that starts delivery? Who observes "completed" before delivery finishes?
3. What is "idle": a daemon idle-shutdown timer? What is "matching" beyond command identity (request id? arguments?)?
4. With "latest per-request promise" and duplicate streams: if a second stream attaches for the same request, does the turn stop waiting for the first stream? Can the FIFO open while an earlier stream is still delivering?
5. When is a delivery "absent tracking"? Is that the normal case when no client fetches the result, and does the turn then complete immediately?
6. What does the "resource sample" measure, and what is "that barrier" concretely?
7. What does "warm-up sampling still gates admission" mean operationally? Where does warm-up happen relative to A?
8. What does "workspace-deletion shutdown adds its own acknowledgement wait" do? Does it hold the FIFO, and for how long (a timeout?)?
9. What is "physical cleanup" (deleting stored result bytes?), what is "transfer identity", and does a failed cleanup leak storage?
10. The key says #147 moves acceptance metadata "into the ledger", yet the grid colors A as execution-session (teal), not ledger (lavender). Which owns acceptance?
11. Did any of A-I change behaviorally between main and #149, or only ownership? The shapes are constant, but "Stable color does not mean unchanged code."
12. Why is D owned by the ledger even on main, before any of this refactor?
13. What are the "app-owned mechanisms" #149 removes, and what is the "frozen CLI graph"?
14. Which timing expectations were removed exactly, and is timing covered elsewhere (the page says it does not establish this)?
15. What changed in #123-#144? The page scopes them out ("outside this narrow lens"), but their row labels suggest daemon-relevant changes (admission authority, failure vocabulary, result receiver, execution recovery).
