## 2. The change in at most three sentences

Across the stack (ending in #148/#149), the CLI's client-side result-delivery machinery — raw socket I/O,
recovery of accepted requests, transfer continuity, and output capture — is taken out of a shared CLI source file
and given one file per role inside the daemon package; #148 stages the package and #149 switches the CLI to it,
while all of it still runs in the client process. The recovery semantics are carried over: an interrupted
transfer (after acceptance + manifest) fetches from the first record not yet appended while keeping its receiver
and capture, and a qualifying accepted close reattaches the identical execute request with a fresh
receiver/capture, relying on daemon-side idempotency to avoid re-execution. Fixed one-shot recovery becomes two
independent numeric budgets whose defaults stay at 1, and the transport tests move into the package suite with
added tests for limits, capture disposal and exhausted-fetch corruption.

## 3. Boxes and boundaries

- **Process boundary (did not move):** CLI/client process vs daemon process, separated by a socket hop
  (map: dashed vertical "fixed runtime boundary"). All four roles "still run client-side on this path".
  Daemon/server context is "outside the role census" (map label) — the page does not analyse daemon internals
  except to cite its "duplicate identity path".
- **Package boundary (moved):** `apps/cli` vs `packages/daemon`. Reading 01: "On main, three share one CLI
  source file. At #149, each has a package file". The map's moving "front" = this package boundary.
- **Units (roles) inside the client process at #149** (readings name the roles; file names are from the
  default map labels, not the readings):
  1. socket I/O — "Socket client", `socket-client.ts`, raw I/O
  2. accepted recovery — "Execution client", `execution-client.ts`
  3. transfer continuity — "Transfer receiver", `result-transfer-receiver.ts` (receiver, manifest, digest
     progress, next offset)
  4. output capture — "Output capture", `client-result-capture.ts` (records appended)
- **On main:** three of these four shared one CLI source file (readings do not say which three, nor where the
  fourth lived).
- **Sequencing:** #148 stages the package; #149 switches the CLI consumer. #138, #139, #142, #147 are cited for
  reasons (coordination/package boundaries, resume offset, new vs. resumed delivery, idempotency, budgets, tests).
- **State lifetimes across a break:** connection + decoder: per connection (fresh); receiver, manifest, digest
  progress, capture: survive a fetch resume; on reattach: fresh receiver + fresh capture, interrupted capture
  disposed; execute request identity: unchanged across reattach.

## 5. Questions the top layer left open

1. Which path runs when? Fetch needs "acceptance and a manifest"; reattach needs "closed + accepted + same
   authenticated instance". Is the split simply manifest-present → fetch, manifest-absent → reattach? What
   happens if the fetch budget is exhausted with a non-clean (error) close rather than clean EOF?
2. What happens before acceptance (close/timeout before the daemon accepts)? Is there a completion deadline
   there, and is it retried at all?
3. What is "accepted corruption" concretely (error type / exit code / what the user sees)?
4. What does "return the first accepted close" mean for the caller — the first close's error is surfaced
   instead of the last one's? Why first?
5. With the completion deadline removed after acceptance, can an accepted request hang forever? Any other bound?
6. Acknowledgement: who acknowledges whom (client acks daemon? daemon acks client?), and what does a failed
   ack mean for a result the user may already have seen?
7. Does a reattachment (new execute attempt) reset the per-attempt fetch budget, so defaults could allow up to
   2 attempts × 2 fetches? Is that intended?
8. Where are the budgets configured (flag, config, code-only), and who can set them? What is the "policy record"
   (a doc? a file?) — it is cited twice but never described.
9. "same authenticated instance" — what identity is checked and how?
10. "What counts as corrupt" vs "interrupted" (digest mismatch? decode error? manifest mismatch)?
11. On main, which three roles shared the CLI file, where did output capture live, and what exactly was the
    "fixed one-shot recovery"?
12. Roles of individual PRs: #139 and #147 are cited only as reasons; what did each change? The stack has 26
    PRs; which of them does this slice cover?
13. Tests: 14 titles retained out of how many on main? Were any tests deleted, renamed or weakened? The page
    pointedly "does not equate matching test names with matching assertions" — did assertions change?
14. Does moving client-side code into `packages/daemon` create any dependency/packaging consequence for the
    CLI (e.g., the daemon package now ships client code)?
15. What is "digest progress" (running hash over records?) and is it verified at completion together with the
    manifest?
