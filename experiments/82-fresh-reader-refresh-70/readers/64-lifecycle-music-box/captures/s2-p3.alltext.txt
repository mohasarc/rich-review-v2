  THE COMPLETE SCORE NOTES
  What the notes mean.
  This is the complete stopping layer. Every decision and surprise in the optional source depth is named here.
  Stated
  means a reason was found;
  unexplained
  means it was not found in the supplied PR, commits or relevant spec.
  01
  One lifetime owner. Six separate voices.
  The TypeScript service still owns its instance and query algorithms; core now supplies
  TurnScopedCacheScope
  and six isolated typed handles. Key spaces and cached identities stay separate. No package dependency direction changes. Five identity stores hold promises; position storage holds locations.
  Stated
  — lifetime belongs in core; independent key/value spaces need separate handles. Preserving algorithms and identities is the PR’s stated scope.
  Solo + inspect ↗
  02
  The clearing chord comes after a successful refresh.
  Source cache → project graph (workspace coverage only) → workspace state → begin turn. A failed state refresh skips the chord and keeps the old entry, even though earlier refresh work has run. This order is preserved; the service now receives readonly files instead of the full snapshot.
  Stated
  — failed refresh must preserve the current successful turn.
  Unexplained
  — why narrow the argument.
  Solo + inspect ↗
  03
  Clearing is immediate. Completion now waits.
  Both versions clear synchronously before project release. #127 adds an await in service and backend, carrying project rejection to the backend caller. #126 can fulfill while the graph is pending and leave its rejection unhandled. Today’s concrete cleanup is synchronous; our long wait is injected. The graph already releases projects sequentially and stops at the first failure.
  Stated
  — old semantics must be unavailable during pending or rejecting release.
  Unexplained
  — rationale for changed completion/failure behavior: the PR names the awaited boundary while claiming failure behavior is preserved.
  Solo + inspect ↗
  04
  Silencing the entries does not stop the players.
  Both lifecycle methods synchronously call the same private clear. Handles remain reusable: a direct query can refill during pending release, and that entry survives completion. Clearing does not cancel old promises; a late answer cannot replace a new entry because the value is stored at creation, not settlement.
  Unexplained
  — no specific rationale for two verbs over one clear, reusable handles, or the late-settlement policy. These are source/test contracts; the refill and late-answer recordings agree with them.
  Solo + inspect ↗
  05
  A quiet result still counts as a result.
  Map.has
  makes cached
  undefined
  valid. Exact factory values—including rejected promises—remain cached for the turn. A synchronous factory throw stores nothing and retries. Reference and position projections still rebuild public results from cached locations; a cached entry does not mean every returned wrapper shares identity.
  Stated
  — preserve valid undefined values and existing query/failure behavior.
  Unexplained
  — the original reasons for the projection and error-policy distinctions.
  Inspect source ↗
  06
  A small public instrument, newly pinned.
  Core exports the scope and typed
  getOrCreate
  handle; lifecycle methods return void, while service release now returns a promise. Six service tests and four core tests are added; the five old service cases and their helpers are unchanged. The release test uses a held fake graph, and later-project skipping is asserted through that fake. This is bounded evidence, not full daemon parity.
  Stated
  — commit subjects characterize identities and specify lifecycle/awaited release.
  Unexplained
  — why this public API shape or this exact test selection. No removed or weakened cases in the two changed suites.
