## 2. The change in at most three sentences

PR #127 moves ownership of turn-scoped cache lifetime out of the TypeScript query service and into core. Before, the service cleared six private Maps. Now core supplies a `TurnScopedCacheScope` with six isolated typed `getOrCreate` handles, and the service keeps its instance and query algorithms. Clearing is still synchronous: at turn start after a successful refresh, and at release before the project graph is released. New in #127, the service and backend release methods *await* the project graph's release, so backend release completes only when projects finish releasing and passes project rejection to its caller. Ten tests are added (six service, four core), which by commit subjects characterize identities and specify the lifecycle/awaited release; the release test uses a held fake graph.

## 3. Boxes and boundaries

Units (score lanes, with owner package in small caps on the page):
| unit | package label | what it does in the story |
|---|---|---|
| Backend | BACKEND–TYPESCRIPT | outer release call; in #127 awaits the service |
| Query service | BACKEND–TYPESCRIPT | owns instance + query algorithms; release calls the clear, then the graph release; receives "readonly files" (was: full snapshot) at refresh |
| Cache lifetime | #126: "TYPESCRIPT · SIX MAPS"; #127: "CORE · SIX HANDLES" | the six semantic caches (definition cache named); cleared by a single private clear called from both lifecycle methods |
| Project graph | CORE | releases projects sequentially, stops at first failure (pre-existing); refresh step "(workspace coverage only)" |
| Configured project / Inferred project | BACKEND–TYPESCRIPT | individual project releases, where cleanup is synchronous today (the long hold is injected) |
| Probe / Node | PROBE / NODE | the recording harness that releases the injected hold ("resolve gate") |

Inside the cache boundary: five "identity stores" hold promises; one position storage holds locations; lookup uses `Map.has` (cached `undefined` is a hit); rejected promises stay cached; a synchronous factory throw is not cached.

Boundaries that moved:
1. **Lifetime ownership boundary.** Clearing/lifetime moved from TypeScript (service-private Maps) to core (scope plus handles). No package dependency direction changes, and algorithms and cached identities stay in TS.
2. **Release completion boundary.** In #126 the query service's release returned synchronously and the backend's release settled (default score, step 7) while the project graph was still pending (it settled at step 14), and a graph rejection could go unhandled. In #127 the service settles only after the graph (steps 12→13) and the backend after the service (step 14), and rejection travels up to the backend caller.
3. **Refresh argument boundary (narrowed).** The service now gets readonly files instead of the full snapshot. The refresh order (source cache → project graph → workspace state → begin turn) is unchanged.

Unchanged, per the page: clearing is synchronous and happens before project release; the refresh order; failed refresh keeps the old turn; the graph releases projects sequentially and stops at first failure; the five old service test cases and their helpers.

## 5. Questions the top layer left open

1. Which six caches are they? Only the "definition cache" is named. Which five are the "identity stores", and which is the "position storage"?
2. What are the two lifecycle method names? The page says "two verbs" and shows "begin turn" and release, but not the identifiers.
3. Who calls backend release, and does that caller handle the rejection that now arrives? Could #127 turn a previously silent rejection into a crash or shutdown failure upstream?
4. T10 lets a query during pending release refill the cache, and the entry survives completion. Can that entry come from a project that is being torn down (a stale answer inside the new turn)? The page records the behavior as a contract but not as a risk.
5. The page flags "the PR names the awaited boundary while claiming failure behavior is preserved". So is the propagation of rejection intended or accidental?
6. What does "project graph (workspace coverage only)" mean in the refresh order? What is left out of that step?
7. Which method gets "readonly files instead of the full snapshot", and does the service lose access to anything it used before?
8. Later-project skipping is asserted through a fake graph. Does any test exercise the real graph's stop-at-first-failure behavior with the new await?
9. What happens if a new turn begins while a release is still pending in #127?
10. Did #126 also cache rejected promises and use `Map.has`? "Preserve" implies yes, but that isn't shown.
11. What are the four core tests versus the six service tests?
