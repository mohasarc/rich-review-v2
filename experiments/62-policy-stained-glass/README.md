# policy-stained-glass

## Entry point

Open [index.html](index.html), or run:

```sh
open ~/projects/rich-review-v2/experiments/62-policy-stained-glass/index.html
```

The finished page opens directly from the folder, offline, without a server, installation or live worktree. Select a glass piece, illuminate a policy material, or switch **Before / Required policy**. Numbered cracks lead to their decision records. Every record opens a mechanism and returns to the same record. Source links open a dialog; Escape restores focus. The [source book](evidence.html) is also a standalone page.

Keyboard: Tab reaches glass and controls; Enter/Space selects; arrow keys move between glass pieces. Browser Back and `#glass=status&light=transport&rev=head` preserve a selected view. Ordinary links, the complete decision layer and source book remain usable without JavaScript. Interactive illumination needs JavaScript.

## Declared choices

- Role framing: a learner examining which boundaries survive shared authority. Assigned angle: policy as stained glass. Narrow teaching target: **sharing a policy section does not merge the purposes or scopes of its consumers**.
- Box lenses: static package/module ownership and composition/input contracts. A small process/thread sentence identifies the already-existing snapshot bridge; the windows are not a runtime topology.
- Opening style: picture first, with the lossy mapping stated beside the picture. Two blue cuts display 100 ms and 250 ms; two amber cuts display one allowance per request and one per attempt.
- Shape: the window plus fourteen open records form the complete stopping layer. Fourteen matching mechanisms and their exact source excerpts add fidelity. The opening sentence or picture alone is not claimed to be a complete PR explanation.
- Navigation: direct glass selection, independent material illumination, before/head comparison, numbered crack jumps, record → mechanism → source, exact record returns, previous/next mechanism links, browser history and ordinary document scrolling.
- Trust posture: source-grounded teaching. Stated reasons are attributed to the supplied PR or policy/spec documents. Specific projection, adapter, recovery and test changes retain rationale gaps. There are no verdicts, comments, scores or stored review responses.
- Persona: a teammate who knows Symnav but not this daemon corner.
- Representations used: three consumer-family silhouettes; seven policy materials; required-input lead perimeters; shared purpose seams; base hatching; numbered fractures; material illumination; a nested request/attempt illustration tied to recorded calls; bounded before/head observation tables; exact source disclosures.
- Importance rule: the shared-authority/distinct-purpose distinction first, followed by exceptions to the boundary and changes to the evidence used to characterize it. A source gap gets an open surface record even when it does not fit a pane.
- Inputs used (beyond bundle): pinned head/base source, existing policy implementation and policy tests, `plans/005/daemon-policy.md`, architecture functional spec, contributor guidance, actual compiled transports/output capture, Git object IDs and worktree status, library documentation and an existing geometry spike in this experiment. ## What I tried

The folder already contained unfinished prior attempts: an installed library set, a large inventory draft, a geometry spike and a screenshot helper. I inspected them, preserved them, and built a new, narrower artifact. The old inventory’s counts, history claims and references to nonexistent probes are not shipped as evidence. The new capture checks its own fourteen records against pinned source. The existing screenshot helper was used for the first render.

The retained spike compares a weighted Voronoi treemap, relaxed Voronoi cells and Paper.js band intersections. Irregular automatic cells competed with the purpose labels and made equal areas look meaningful. I chose stable boolean cuts and a four-lobed shape for the paired purposes. No graph routing or semantic camera was necessary.

Final source reconciliation also corrected a draft that attributed an effective-memory → hard-RSS reporting change to production. The base already passed hardProcessRssBytes; record 04 now distinguishes removal of the option from a changed value, and identifies the ignored test option instead.

Source reading prevented two misleading explanations: the base already gave a reattached execution attempt its own fetch allowance, and a numeric fetch limit above one does not create a repeated-fetch loop. Both remain on the complete layer. A first socket probe had an incomplete injected manifest; it failed before fetching. Adding the protocol-required instance ID fixed the harness. The resulting recordings assert their expected outcomes before they are saved.

Browser inspection found a long worker label, an amber label touching the central lead and cracks covering value text. I shortened/repositioned labels and moved the crack badges. A repeated JavaScript-disabled check stalled during long smooth scrolling; document jumps now use immediate native navigation, and the browser check brings that tab to the foreground. The failed-check log is retained under `evidence/browser-failure-before-scroll-fix.*`. A final check tests all text spans against their containing SVG paths. The actual glass partitions are also checked for area coverage and pairwise overlap.

## What I would drop

The translucent facets and outer architectural arch are decorative. They help the material reading, but their removal would preserve the factual encoding. The broad raw-diff census is useful for auditing and earns little space in ordinary reading.

The fourteen open records make the complete layer several screens long. That is the cost of retaining input, adapter and test surprises around a deliberately narrow central lesson. On a phone the whole window is an orientation image; the selected text and records carry the readable detail.

## What I would do next

Ask an unfamiliar reader to predict the wait for the same request sent by two callers, and which allowance is fresh after a reattachment. Compare their explanations with a conventional diagram using the same evidence. No human comprehension trial was performed here.

## Visual-variable legend

| Variable | Factual meaning | Limit |
| --- | --- | --- |
| Pink / green / blue / orange / mint / violet / amber | Output / resources / transport / startup / shutdown / diagnostics / delivery sections | A hue identifies a section, not a value or importance score. Names accompany color. |
| Pointed / four-lobed / round-headed windows | Capacity / purpose-sensitive transport and delivery / lifecycle consumer families | These group modules; they are not physical processes or package silhouettes. |
| Position above/below | Policy definition in `packages/daemon`; consuming mechanisms remain in `apps/cli` | Distance and pane area encode no measurement, chronology or dependency count. |
| Heavy perimeter and shared interior lead | Required policy inputs at principal consumers; distinct purposes within a shared material | Not proof that every downstream API is required. Thin internal facets are decorative. |
| Base hatching and interrupted perimeter | Local numeric defaults/options remain available before the change | A schematic ownership treatment, not a numeric count of bypasses. |
| Numbered white fracture | 04: ignored legacy test option; 08: recovery edges; 09: heterogeneous/optional seams | A source-backed question or rationale gap, never a correctness verdict or measured damage. Other gaps remain in the open register. |
| Illumination | Which displayed consumers use one policy material | Selection is illustrative light, not execution or traffic. |
| Nested amber request/attempt pieces | Reattachment count spans the request; fetch count belongs to an attempt | The page steps through a saved trace. It does not run Symnav or simulate arbitrary faults. |

## Libraries considered and used

| Library | Evaluation and choice |
| --- | --- |
| [Paper.js](https://paperjs.org/reference/pathitem/) 0.12.18 | **Used at build time.** `intersect` and `unite` give reliable cuts and compound curves, with area and overlap checks. Chosen from the retained three-way spike. |
| [SVG.js](https://svgjs.dev/docs/3.2/) 3.2.4 | **Used in the page.** Adopts the generated SVG and manages selection, classes and events. Vendored locally. |
| D3 7.9.0 + d3-voronoi-treemap 1.1.2 | Retained spike demonstrates automatic cells. Not used in the finished view: the geometry is a semantic grouping, not a data-area visualization. |
| d3-delaunay + polygon-clipping 0.15.7 | Retained alternate spike produces relaxed clipped cells. Adds irregularity without improving the two-purpose comparison. Not shipped at runtime. |
| [Rough.js](https://roughjs.com/) 4.6.6 | Considered from local installation and documentation. A sketch treatment would make actual fractures harder to distinguish from normal edges. Not used in the finished artifact. |
| Two.js | Considered as a scene renderer; not installed or executed for this pass. It offered no needed capability beyond the chosen SVG rendering and Paper geometry. |

The retained alternatives remain in `package-lock.json` so the geometry spike stays reproducible. The finished page loads only the small vendored SVG.js bundle. It makes no external requests.

## What the weird form teaches

**Better:** one section can be visually identical material in distinct cuts. Lighting blue reveals a shared transport section spanning frame caps and two different waits. Lighting amber keeps the per-request and per-attempt distinction visible despite both defaults being one. Solid lead versus retained fractures makes required composition and surviving downstream seams coexist in the same picture.

**Worse:** the glass does not express exact call order, TypeScript projection types, error identity or test stimulus changes well. Those use small comparisons, a recorded scope example and source receipts. Shape is learned through a legend; a conventional dependency diagram would be quicker for a reader whose only question is “which file imports which package?” This page is intentionally organized around policy authority and purpose instead.
